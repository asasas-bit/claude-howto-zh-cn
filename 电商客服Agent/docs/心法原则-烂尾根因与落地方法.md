# 项目烂尾根因诊断 + 落地方法论

## Context

用户描述的核心问题：
- 想法 → 框架 → **烂尾** → 学别的东西 → 新想法 → 新框架 → **又烂尾**
- 调试时一个问题修好，另一问题出现，最后全乱了，放弃
- 不知道什么时候该"够用了"，什么时候该继续优化
- 学和做分离——总觉得要"先学好"才能动手

这不是知识不够的问题，而是**做项目的流程和方法本身有问题**。

---

## 一、根因诊断

### 根因 1：目标太大，没有"最小可用的第一步"

电商客服 Agent 这个目标本身包含：
- 客服 Agent
- 监督 Agent
- 入口 Hook + 出口 Hook
- 知识库
- 反馈收集
- 多平台接入

**人一看到这么多东西，大脑就自动放弃**——因为感觉永远做不完。

### 根因 2：没有"快速成功回路"

调试时可能花 3 小时修一个问题，期间没有任何正向反馈，大脑觉得"没进展"，就想逃。

### 根因 3：调试方法不对——随机试，不是系统地试

"调了这个问题，又冒出下一个问题"说明不是修 bug，而是**改了 A 影响了 B**——因为没有隔离测试，改动没有边界。

### 根因 4：不知道"够用了"是什么样子

电商客服 Agent 可以是：
- **v0.1**：一个 Python 脚本，读取一个 JSON 文件里的问答对，返回固定回答
- **v1.0**：能跑通全流程的真实可用版本
- **v2.0**：有 Hooks + 监督 Agent + 反馈收集

总想一步到位做 v2.0，但从来没到过 v1.0。

---

## 二、解决方案：项目落地操作手册

### 原则 1：永远从"能跑通的最小版本"开始

**电商客服 Agent v0.1 是什么？**

一个 Python 文件，硬编码 3 个常见问答：

```python
# customer_service_v0.1.py
questions = {
    "这件衣服多少钱": "299元",
    "可以退换吗": "7天内可以退换，运费自理",
    "什么时候发货": "付款后24小时内发货"
}

user_input = input("你问：")
for q, a in questions.items():
    if q in user_input:
        print("客服：", a)
        break
else:
    print("客服：抱歉，这个问题我暂时回答不了，您可以联系人工客服")
```

**为什么从 v0.1 开始？**
- 5 分钟能跑通
- 有真实的"我问，它答"——大脑获得真实的成就感
- 接下来迭代有基准

### 原则 2：每次只改一个东西

不要同时改：查知识库 + 监督 Agent + Hooks + 反馈收集

正确节奏：
```
v0.1（5分钟）→ 加知识库查询（1天）→ 加飞书接入（1天）→ 加 Hooks（半天）→ 加监督Agent（1天）
```

每步都是在上一步"跑通了"的基础上加东西。

### 原则 3：遇到 bug 先隔离，再修

错误做法：改了代码 A，B 功能坏了，不知道为什么
正确做法：
1. 写一个最小测试脚本，专门测 A 功能
2. A 功能单独跑通
3. 再把 A 放回整体

### 原则 4：给"够用了"一个明确标准

**电商客服 v1.0 的够用标准**：
- 能收到客户消息
- 能查知识库
- 能发出回答
- 回答发出前有一次人工确认

到了这个标准，就算 v1.0 完成，可以上线用。后面持续迭代是优化，不是必须。

## 四、预防烂尾的具体机制

### 机制 1：设"完成仪式"

每个版本完成时：
1. 在 `电商客服Agent/日志/` 下建一个 `v0.1-完成.md`
2. 写：今天完成了什么，下一个版本做什么
3. 发给朋友/自己一句话："v0.1 跑通了！"

**为什么有效**：把进度外化，大脑就觉得"这个项目有进展"，不容易放弃。

### 机制 2：每天只做一件事

不要一天想干完所有事情。

每天开始前问自己："今天只做哪一件事，能让这个项目推进？"

### 机制 3：遇到 bug 不要马上去修

遇到 bug 时：
1. 先记录：`bug: xxx，今天日期`
2. 问："这个问题不修，最坏能坏到什么程度？"
3. 如果不是阻断性的，放进"待修 list"，继续往前走
4. 阻断性的才停下来修

### 机制 4：准备好"放弃清单"

每个项目开始时，写下：
- 做到什么程度就算"这个项目暂时到这里可以停了"
- 什么时候算"彻底失败，要认输"

避免：无限期拖着一个半成品，既不完成也不放弃。

## 六、针对你的四个根因，对症下药

### 根因 1：遇到问题解决不了 → **调试系统**

**方法**：
1. 遇到 bug，先问："这个问题不修，最坏能坏到哪里？"
2. 如果不是阻断性的，**记下来，继续往前走**
3. 如果是阻断性的，用这个顺序解决：
   - Google / GPT 搜错误信息（90%的问题已经被别人解决过）
   - 最小复现：写一个只测这个 bug 的 5 行脚本
   - 问人（朋友/群/论坛）

**关键心态**：遇到问题不解决不了，是因为你一个人在死磕。**问人不是弱，是方法**。

---

### 根因 2：觉得自己技术不够 → **重新定义"够用了"**

**真相**：v0.1 完全不需要高深技术，就是一个 `if...else` 脚本。

**重新定义**：
- 不是"我技术不行做不了" → 而是"这个阶段不需要那么高技术"
- "够用了" = **能跑通最小流程**，不是"代码完美"

---

### 根因 3：目标太大 → **强制切割到"今天只做一件"**

**方法**：
1. 每天开始前，只问自己一个问题："**今天做哪一件事，能让项目往前推一步？**"
2. 把这件事写成一行，写在 `src/今日目标.md`
3. 做完今天的这一件，才算完成

**这个项目拆解到"今天只做一件"**：
- 今天：写 v0.1 硬编码脚本，跑通（5分钟）
- 明天：加 Claude API 调用（1小时）
- 后天：接飞书消息（半天）
- 大后天：接知识库（半天）
- 第五天：v1.0 完成

---

### 根因 4：越做越难 → **每次只动一个东西，测试后再动下一个**

**错误模式**：
```
改了 A → 测试 → 坏了 → 修 A → 又影响 B → 改 B → 彻底乱了 → 放弃
```

**正确模式**：
```
改动前：备份当前版本（git commit）
改 A：单独改 A → 测试 A 是否 work → 如果 work 才改下一个
改 B：单独改 B → 测试 B 是否 work
每改完一个：commit 一次
```

**Git 就是你的后悔药**——每次改东西前 commit一次，乱了可以回退。

### 第一步：建一个文件 `v0.1_hardcoded.py`

内容（可以直接复制）：

```python
"""电商客服 Agent v0.1 - 硬编码版
5分钟跑通：问我"这件衣服多少钱"，它答"299元"
"""

# 硬编码问答知识库
KNOWLEDGE = {
    "这件衣服多少钱": "299元",
    "可以退换吗": "7天内可以退换，运费自理",
    "什么时候发货": "付款后24小时内发货",
    "有优惠券吗": "目前新用户首单减10元，可以点击领取",
}

def answer(question: str) -> str:
    """根据用户问题，返回固定回答"""
    for q, a in KNOWLEDGE.items():
        if q in question:
            return a
    return "抱歉，这个问题我暂时回答不了，您可以联系人工客服"

# 测试
if __name__ == "__main__":
    test_questions = [
        "这件衣服多少钱",
        "可以退换吗",
        "我想退",
        "你有女朋友吗",
    ]
    print("=== 电商客服 Agent v0.1 测试 ===\n")
    for q in test_questions:
        print(f"客户问：{q}")
        print(f"客服答：{answer(q)}\n")
```
