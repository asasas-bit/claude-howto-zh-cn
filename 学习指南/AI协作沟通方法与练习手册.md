# AI 协作沟通方法与练习手册

这份指南不要求你学习“高级提示词技巧”。它的目标是让你从：

> 我说一句，看看 AI 随机做成什么样

逐步变成：

> 我能说清目标，控制修改范围，检查结果，并把成功方法保存下来

Claude Code 和 Codex 都可以使用这里的方法。

## 一、先理解：你不是在考试，而是在协作

和 coding agent 沟通，不需要一次写出完美提示词。

更稳定的方式是一个闭环：

```text
检查现状 → 对齐目标 → 制订方案 → 授权执行 → 验证结果 → 总结交付
```

每一步都解决一个不同问题：

| 阶段 | 你要解决的问题 | 推荐说法 |
|---|---|---|
| 检查现状 | AI 是否真的了解项目 | “先阅读相关文件，暂时不要修改。” |
| 对齐目标 | 双方理解的是不是同一个结果 | “请复述你理解的目标和完成标准。” |
| 制订方案 | 准备改哪里，有什么风险 | “列出步骤、涉及文件和风险。” |
| 授权执行 | 允许它做到什么程度 | “只修改以下文件，其他文件不要动。” |
| 验证结果 | 怎样证明不是表面完成 | “运行检查，并说明验证结果。” |
| 总结交付 | 我应该重点看什么 | “总结改动、证据、风险和下一步。” |

## 二、一条稳定任务的六个组成部分

### 1. 背景

告诉 AI 当前在处理什么，但不要把无关故事全部塞进去。

```text
这是一个面向中国小白的 Claude Code 中文教程仓库，
主体内容是 Markdown 文档。
```

### 2. 目标

说“最终得到什么”，不要只说“帮我优化一下”。

模糊：

```text
帮我优化学习地图。
```

清楚：

```text
把学习地图改成纯新手可以按顺序执行的入门指南，
并补充每一步的目的、操作和自检标准。
```

### 3. 范围

明确可以碰什么、不可以碰什么。

```text
只允许修改 LEARNING-ROADMAP.md。
可以读取其他章节作为参考，但不要修改它们。
```

### 4. 约束

告诉 AI 必须保留的东西。

```text
不要翻译命令名、文件路径、frontmatter key 和代码块中的可执行命令。
面向没有终端基础的 Windows 用户。
```

### 5. 验收标准

定义怎样才叫完成。

```text
完成后必须满足：
1. 每个阶段都有目的、练习和自检标准
2. Bash 命令旁有 PowerShell 说明
3. 所有相对链接仍然有效
4. 不覆盖现有 CLAUDE.md
```

### 6. 权限与汇报

说明是否先出方案，以及完成后怎样汇报。

```text
先检查并给出方案，暂时不要修改。
我确认后再执行。

执行完成后告诉我：
1. 修改了哪些文件
2. 做了哪些验证
3. 还有哪些不确定或风险
```

## 三、最适合小白的五步协作法

### 第一步：让 AI 先读，不要改

可直接复制：

```text
先阅读当前项目的 README、项目说明文件和与任务有关的文件。
暂时不要修改，也不要创建新文件。

请告诉我：
1. 这个项目是做什么的
2. 和本任务最相关的文件有哪些
3. 你目前有哪些不确定
```

这一步能防止 AI 只凭文件名猜项目。

### 第二步：让 AI 把任务说回来

```text
请用自己的话复述你理解的目标。
同时列出：
1. 什么属于本次范围
2. 什么不属于本次范围
3. 什么情况算完成
```

如果复述不对，这时纠正最省成本。

### 第三步：复杂任务先要方案

```text
先给我一个实施方案，不要修改文件。

方案需要包括：
1. 修改步骤
2. 涉及文件
3. 每一步的验证方法
4. 可能的风险
5. 需要我决定的问题
```

小修改不必强制长计划。判断标准是：改错以后是否难以发现或恢复。

### 第四步：小范围授权执行

```text
按刚才确认的方案执行。

只允许修改：
- 文件 A
- 文件 B

不要：
- 安装新依赖
- 修改配置文件
- 删除现有内容
- 执行发布或推送
```

第一次合作时，范围宁可小一点。

### 第五步：要求验证和证据

```text
完成后请自行检查，不要只告诉我“已经完成”。

请提供：
1. 实际修改的文件
2. 运行的检查或测试
3. 检查结果
4. 未验证的部分
5. 我最应该人工查看的地方
```

“已经完成”是结论，“测试通过、链接有效、diff 符合范围”才是证据。

## 四、先区分你到底在要求哪种任务

| 任务类型 | 你真正要的结果 | 推荐开头 | 默认是否允许修改 |
|---|---|---|---|
| 解释 | 帮我看懂现状和概念 | “阅读后用小白能懂的话解释……” | 否 |
| 调查 | 找到事实、位置和影响范围 | “先定位相关文件和调用关系……” | 否 |
| 诊断 | 找到问题原因 | “复现或分析原因，先不要修复……” | 否 |
| 修改 | 实际改变文件 | “在以下范围内实现……” | 是，限指定范围 |
| 审查 | 找缺陷、风险和遗漏 | “审查当前 diff，按严重程度报告……” | 否 |
| 自动化 | 把重复工作变成稳定流程 | “先记录现有人工步骤，再判断适合 command、Skill 还是 Hook……” | 分阶段授权 |

最常见的沟通问题，是你只想“查原因”，AI 却直接修改；或者你想“完成修复”，AI 只给建议。

## 五、可直接复制的常用模板

### 模板 A：看懂一个陌生项目

```text
请先阅读这个项目，不要修改任何文件。

我是新手，请用通俗中文回答：
1. 这个项目解决什么问题
2. 主要目录分别做什么
3. 从哪里启动或使用
4. 最重要的三个配置文件
5. 如果我要开始学习，建议先看哪三个文件

遇到术语时，先用一句大白话解释，再补充准确名称。
```

### 模板 B：做一个小修改

```text
目标：
[写最终想得到什么]

范围：
只允许修改 [文件或目录]。

要求：
- [必须保留的内容]
- [用户或技术限制]
- [输出风格]

验收：
- [检查 1]
- [检查 2]

先检查相关文件并说明准备怎么改。
如果没有阻塞问题，就直接执行并验证。
完成后总结改动、验证结果和剩余风险。
```

### 模板 C：只诊断，不修复

```text
请调查 [问题现象]。

本轮只诊断原因，不修改文件、不安装依赖。

请提供：
1. 最可能的根因
2. 支持这个判断的文件、日志或命令输出
3. 其他可能性及为什么优先级较低
4. 最小修复方案
5. 修复后应该怎样验证
```

### 模板 D：审查 AI 刚做的修改

```text
请审查当前修改，不要继续改文件。

重点检查：
1. 是否超出原任务范围
2. 是否改变了不该改变的行为
3. 是否有遗漏、错误链接或错误命令
4. 是否完成了要求的验证
5. 是否存在安全或数据风险

先报告真实问题；如果没有发现问题，也请说明检查了什么。
```

### 模板 E：把重复流程做成能力

```text
下面这套工作我已经重复做过多次：
[描述实际步骤]

请先分析它更适合：
- 一次性提示词
- slash command
- Skill
- Hook
- MCP
- Subagent

先解释选择理由，不要创建文件。
同时列出输入、步骤、输出、验收方式和风险。
```

## 六、当前仓库的完整示例

### 第一轮：只调查

```text
请阅读：
- LEARNING-ROADMAP.md
- CATALOG.md
- 01-slash-commands/README.md
- 02-memory/README.md

暂时不要修改文件。

我是只会和 AI 普通对话的新手。
请指出学习路线中最容易让我误解的五个地方，
并区分哪些是概念问题、哪些是 Bash/PowerShell 命令问题。
```

### 第二轮：确认目标

```text
我的目标不是增加更多高级功能，
而是让 Windows 小白知道：
1. 每一步在做什么
2. 应该在哪个目录执行
3. 执行后会出现什么文件
4. 怎样判断成功
5. 怎样安全撤回

请据此给出修改方案，暂时不要修改。
```

### 第三轮：授权修改

```text
按确认后的方案执行。

只允许修改 LEARNING-ROADMAP.md。
不要覆盖 CLAUDE.md，不要修改示例命令，不要安装依赖。

完成后检查：
- Markdown 相对链接
- 命令路径
- Bash 与 PowerShell 的差异说明
- 是否仍然符合原有学习阶段
```

### 第四轮：验收

```text
请停止继续修改，审查当前 diff。

按照“目标、范围、约束、验收标准”逐条判断是否通过。
把未通过或未验证的项目单独列出。
```

## 七、十种容易造成“抽卡感”的说法

| 容易抽卡的说法 | 问题在哪里 | 更稳定的说法 |
|---|---|---|
| “帮我优化一下” | 不知道优化什么 | “提高小白可读性，不改变技术含义” |
| “你看着办” | 范围和取舍全交给 AI | “在这三个文件内自行决定实现细节” |
| “做得专业一点” | 没有可验证标准 | “增加术语解释、例子和自检清单” |
| “修一下这个项目” | 不知道具体故障 | “先复现登录失败并定位根因，本轮不修” |
| “全部完善” | 容易无限扩张 | “只补齐安装、运行、验证三个缺失部分” |
| “不要出错” | 无法操作化 | “运行测试并列出未覆盖场景” |
| “和以前一样” | AI 未必拥有那段上下文 | “按这个示例的标题、表格和语气” |
| “直接干” | 高风险任务没有检查点 | “先确认相关文件；无阻塞再执行” |
| “用最好的方法” | 没有说明成本和偏好 | “优先最小改动，不新增依赖” |
| “完成了吗？” | 容易只得到口头确认 | “列出验证命令、结果和未验证项” |

## 八、任务过程中怎样继续沟通

### AI 理解错了

不要全部重来，指出偏差：

```text
你对目标的理解有一处偏差：
我需要的是 [正确目标]，不是 [错误理解]。

保留已经确认的范围和约束，
重新给出受影响的步骤即可。
```

### AI 做得太大

```text
暂停扩展范围。
本轮只完成最小闭环：
[最小目标]

其他建议放到“后续可选项”，不要现在实施。
```

### AI 卡住了

```text
请区分：
1. 已确认的事实
2. 你的推测
3. 真正阻塞执行的信息
4. 可以用只读检查继续确认的内容

先完成不需要我决定的检查。
```

### AI 说完成了，但你看不懂

```text
请面向不懂代码的人解释本次结果：
1. 原来是什么状态
2. 现在变成什么状态
3. 哪个文件最值得我打开查看
4. 我怎样手动确认它有效
5. 如果不满意怎样撤回
```

## 九、什么时候应该先计划，什么时候可以直接做

| 情况 | 建议 |
|---|---|
| 只改一处错别字 | 直接修改并检查 |
| 新建一份独立说明文档 | 简短确认结构后直接做 |
| 修改多个相关文件 | 先列出影响范围和步骤 |
| 安装依赖、改数据库、改权限 | 必须先说明风险和回退方法 |
| 发布、推送、发消息、操作外部系统 | 先确认目标和外部影响 |
| 删除文件或批量重写 | 先查看 diff、备份或 Git 状态 |
| 任务描述本身有多种合理解释 | 先对齐目标和取舍 |

计划的目的不是让输出更长，而是尽早发现理解偏差和风险。

## 十、七次练习：从聊天到稳定协作

| 次数 | 练习任务 | 重点能力 | 通过标准 |
|---|---|---|---|
| 1 | 让 AI 解释一个目录，不修改 | 区分解释和修改 | 能指出相关文件并承认不确定性 |
| 2 | 修改一段 Markdown | 目标、范围、约束 | 只改指定文件 |
| 3 | 让 AI 先计划再修改 | 分阶段授权 | 计划与最终修改一致 |
| 4 | 故意要求一个小改动后查看 diff | 验收和证据 | 你能说出实际改了什么 |
| 5 | 制造一个可撤回的小实验 | Checkpoint / Git | 能恢复到修改前 |
| 6 | 写最小 `CLAUDE.md` 或 `AGENTS.md` | 长期项目说明 | 新会话能复述关键规则 |
| 7 | 重复一个已经成功的流程 | 判断复用方式 | 能解释该用普通提示词、command 还是 Skill |

不要一天完成全部。每次只练一个能力，效果更好。

## 十一、提交任务前的自检清单

### 我有没有说清楚

- [ ] 最终想得到什么
- [ ] 可以修改哪些文件
- [ ] 哪些东西不能动
- [ ] 面向什么用户或环境
- [ ] 什么情况算完成

### AI 有没有说清楚

- [ ] 它检查了哪些文件
- [ ] 它准备怎么做
- [ ] 它实际改了什么
- [ ] 它运行了哪些验证
- [ ] 哪些部分仍然没有验证

### 安全上有没有遗漏

- [ ] 是否涉及删除、覆盖或批量修改
- [ ] 是否涉及安装依赖
- [ ] 是否涉及密钥和账号
- [ ] 是否涉及发布、推送或外部消息
- [ ] 是否有 checkpoint、Git 或备份

## 十二、最终记忆模板

以后不知道怎么说时，只要填写下面这段：

```text
背景：
[这个项目或文件是做什么的]

目标：
[最终要得到什么]

范围：
[允许读取和修改什么]

约束：
[不能碰什么，必须保留什么]

验收：
[怎样判断真的完成]

执行方式：
[先调查还是直接执行；是否需要先给方案]

完成后：
请汇报修改文件、验证证据、剩余风险和撤回方法。
```

提示词不需要华丽。稳定协作的关键是：目标明确、范围可控、结果可验、失败可退。
