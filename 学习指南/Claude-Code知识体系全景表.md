# Claude Code 知识体系全景表

这份表不是让你背功能，而是帮助你快速判断：

- 这个概念是做什么的
- 它解决什么实际问题
- 学完以后你能做出什么
- 现在要不要学
- 应该去本仓库哪里看

如果你目前只是会和 AI 对话，先看“推荐阶段”列，只学习“现在”标记的内容即可。

## 一、先看懂完整知识地图

| 顺序 | 知识点 | 用大白话解释 | 主要解决的问题 | 学完后的实际产物或动作 | 推荐阶段 | 仓库入口 |
|---|---|---|---|---|---|---|
| 1 | Slash Commands | 给一段常用提示词起一个短名字，像给工作流做一个按钮 | 同样的要求不必每次重新输入 | 安装一个 `.md` 命令文件，并用 `/optimize` 等名称调用 | 现在，先体验一次 | [01-slash-commands](../01-slash-commands/README.md) |
| 2 | Memory / `CLAUDE.md` | 给 Claude Code 的项目员工手册 | 不必每次重复说明项目背景、规范和常用命令 | 项目根目录的 `CLAUDE.md`、个人或目录级记忆 | 现在，重点掌握 | [02-memory](../02-memory/README.md) |
| 3 | Checkpoints / Rewind | Claude Code 会话里的后悔药 | 尝试失败后不敢撤回，或者不知道回到哪一步 | 查看 checkpoint，用 `/rewind` 或快捷键回到较早状态 | 现在，重点掌握 | [08-checkpoints](../08-checkpoints/README.md) |
| 4 | CLI 基础 | 从终端启动和控制 Claude Code | 只会聊天，不知道怎样指定目录、恢复会话或处理管道输入 | 使用 `claude`、`claude -p`、`--continue`、`--resume` | 现在，掌握高频部分 | [10-cli](../10-cli/README.md) |
| 5 | Skills | 把一套稳定的工作方法做成可复用能力 | 工作流不只是一个短提示词，还需要规则、脚本、模板或参考资料 | 一个包含 `SKILL.md` 的目录 | 同一流程重复几次后 | [03-skills](../03-skills/README.md) |
| 6 | Hooks | 在特定时机自动执行检查、提醒或拦截 | 经常忘记格式化、测试、安全检查或记录结果 | `settings.json` 中的 hook 配置和配套脚本 | 有明确自动检查需求时 | [06-hooks](../06-hooks/README.md) |
| 7 | MCP | 给 Claude Code 接上外部工具和实时数据 | 模型无法直接访问 GitHub、数据库、文件服务或业务系统 | MCP server 配置、登录授权和可调用工具 | 确实需要外部数据时 | [05-mcp](../05-mcp/README.md) |
| 8 | Subagents | 把独立子任务分给专门助手 | 一个任务太大，主会话上下文混乱，或者多个部分可以并行处理 | `.claude/agents/` 下的专业 agent 定义 | 单个任务已经明显复杂时 | [04-subagents](../04-subagents/README.md) |
| 9 | Advanced Features | 控制复杂任务怎样规划、授权、运行和恢复 | 任务跨度大、运行时间长、权限边界复杂 | plan、权限模式、后台任务、会话、worktree 等组合工作流 | 能独立完成普通任务后 | [09-advanced-features](../09-advanced-features/README.md) |
| 10 | Plugins | 把 commands、skills、hooks、MCP、agents 打成安装包 | 一套能力需要交给多个项目或团队安装和升级 | 带 manifest 的完整 plugin 目录 | 要分发给团队时 | [07-plugins](../07-plugins/README.md) |
| 11 | CLI 自动化 | 让 Claude Code 成为脚本或 CI/CD 的一个步骤 | 人工操作太多，需要批量、定时或流水线运行 | 结构化输出、管道、脚本、CI 任务 | 基础 CLI 熟练以后 | [10-cli](../10-cli/README.md) |

## 二、每个知识点到底应该学到什么程度

### 1. Slash Commands

| 要看懂的内容 | 小白标准 |
|---|---|
| 内建命令 | 知道 `/help`、`/context`、`/model`、`/rewind` 等命令不需要自己安装 |
| 自定义命令 | 知道 `.claude/commands/example.md` 本质上是一份保存下来的提示词 |
| 命令名 | 知道文件名通常决定调用名，例如 `optimize.md` 对应 `/optimize` |
| 参数和引用 | 见到 `$ARGUMENTS`、`$0`、`@path` 时知道它们是动态输入或文件引用 |
| 升级时机 | 短小、由人主动触发的流程可以保留为 command；复杂流程再考虑 Skill |

**最小练习**：安装一个低风险命令，打开它的 Markdown 原文，再调用一次。重点不是输出有多好，而是理解“文件内容如何变成一次调用”。

### 2. Memory

| 要看懂的内容 | 小白标准 |
|---|---|
| 项目规则 | 会把项目定位、常用命令、禁止事项和验收要求写进 `CLAUDE.md` |
| 个人偏好 | 知道个人偏好和项目规则不应全部混在一个文件里 |
| 目录级规则 | 知道不同子目录可以有更具体的协作要求 |
| 优先级 | 明白当前任务中明确说出的要求，通常比长期默认说明更具体 |
| 维护 | 项目变化后会同步修改 memory，不让说明文件和真实项目脱节 |

**最小练习**：不要直接复制虚构项目模板。先让 Claude 阅读真实项目，再生成一份不超过 30 行的 `CLAUDE.md` 草案，由你确认后保存。

### 3. Checkpoints 与 Git

| 工具 | 适合解决什么 | 不应该误解成什么 |
|---|---|---|
| Checkpoint / Rewind | 回看会话、恢复较早状态、尝试不同方向 | 长期版本管理 |
| `git diff` | 查看文件到底改了什么 | 自动判断修改一定正确 |
| Git commit | 保存一个可长期追踪的项目版本 | 每说一句话都必须提交 |
| Git branch / worktree | 隔离较大实验或并行任务 | 新建普通文件夹 |

**核心原则**：checkpoint 管会话试错，Git 管项目历史。重要项目不要只依赖其中一个。

### 4. CLI

| 使用方式 | 大白话解释 | 适合场景 |
|---|---|---|
| `claude` | 进入持续对话 | 边看边改、需要反复确认 |
| `claude "任务"` | 带着第一条任务进入对话 | 快速开始一个明确任务 |
| `claude -p "任务"` | 执行一次，输出结果后退出 | 脚本、管道、批处理、CI |
| pipe 管道 | 把前一个命令的输出交给 Claude | 分析日志、测试失败或文本数据 |
| resume / continue | 继续以前的会话 | 长任务中断后继续 |

**小白先学**：交互模式、`-p` 的区别，以及怎样确认自己当前所在目录。其他 flags 用到再查。

### 5. Skills

一个 Skill 通常是：

```text
skill-name/
├── SKILL.md
├── scripts/       可选
├── references/    可选
└── assets/        可选
```

| 部分 | 作用 |
|---|---|
| `name` | Skill 的稳定名称 |
| `description` | 告诉 Claude 什么时候应该使用它 |
| 正文说明 | 规定完整操作步骤、边界和验收方式 |
| `scripts/` | 放需要重复执行的确定性脚本 |
| `references/` | 放规则、接口文档和领域知识 |
| `assets/` | 放模板、图片或其他产物素材 |

**升级判断**：一套流程已经实际成功执行过几次，而且你能明确说出输入、步骤、输出和验收标准，再做成 Skill。

### 6. Hooks

Hooks 是“事件发生时自动做事”。

| 例子 | 触发时机 | 自动动作 |
|---|---|---|
| 修改文件后格式化 | 写入文件之后 | 运行格式化工具 |
| 危险命令检查 | 执行工具之前 | 阻止或提醒高风险操作 |
| 提交前测试 | 准备提交代码时 | 运行测试或 lint |
| 会话结束记录 | Session 结束时 | 保存摘要或进度 |

**最大风险**：Hook 里的命令是真实执行的。不要复制自己看不懂的 shell、Python 或 Node 脚本，更不要把密钥直接写进去。

### 7. MCP

MCP 可以理解成 AI 的标准扩展接口。

```text
Claude Code → MCP server → GitHub / 数据库 / 文件系统 / 业务 API
```

| 先确认什么 | 为什么 |
|---|---|
| 数据来源是否可信 | MCP 可能读到真实业务数据 |
| 授权范围有多大 | 只读权限和可写权限风险完全不同 |
| Token 放在哪里 | 密钥不应提交到 Git |
| Windows、PowerShell、WSL 用哪一个 | 本地 server 的启动命令可能不同 |
| 失败时是否影响主任务 | 外部服务和网络可能不稳定 |

**小白原则**：第一次只接一个、优先只读、用完会检查权限。

### 8. Subagents

| 适合拆分 | 不适合拆分 |
|---|---|
| 三个互不依赖的模块分别调查 | 一个五分钟就能完成的小修改 |
| 一个 agent 查资料，一个 agent 审查代码 | 多个 agent 同时编辑同一文件 |
| 大仓库中不同目录的并行探索 | 任务边界还没想清楚 |
| 实现、测试、文档职责明确分离 | 只是为了“看起来高级” |

**判断问题**：这些子任务能否分别说清输入、输出和完成标准？如果不能，先不要拆。

### 9. Plugins

Plugin 是分发单位，不是入门必需品。它可以把多种能力组合起来：

```text
Plugin
├── commands / skills
├── agents
├── hooks
├── MCP 配置
├── scripts / assets
└── manifest
```

只有当你已经有一套稳定能力，并且需要给别人安装、升级、版本化时，Plugin 才真正有价值。

## 三、高级功能拆解表

`09-advanced-features` 里包含很多名称。它们不是一个功能，而是一组“复杂任务控制工具”。

| 高级能力 | 大白话解释 | 什么时候有价值 | 新手风险 |
|---|---|---|---|
| Planning mode | 先调查和制订方案，不立即改文件 | 多文件、跨模块、高风险任务 | 把计划当成正确答案，不再核对事实 |
| Permission modes | 决定哪些操作需要询问、哪些可以自动执行 | 想减少重复确认，同时保留安全边界 | 为省事直接放开所有权限 |
| Print mode | 一次性执行并输出，适合机器调用 | 脚本、批处理、CI | 没有限制轮数、工具和输出格式 |
| Background tasks | 让耗时任务在后台继续 | 构建、测试、监控、长时间命令 | 忘记查看状态和最终结果 |
| Monitor | 持续观察长任务状态 | 服务启动、部署、测试矩阵 | 只监控不设结束条件 |
| Scheduled tasks | 到指定时间自动运行 | 定期检查、报告和维护 | 自动执行范围过大 |
| Sessions | 保存、命名、恢复上下文 | 任务跨多个时间段 | 会话太长却不总结 |
| Agent Teams | 多个 agent 共同处理较大任务 | 明确可并行的复杂项目 | 成本、冲突和协调开销增加 |
| Dynamic workflows | 运行时组织多步骤工作流 | 步骤会根据中间结果变化 | 流程不可预测、难验收 |
| Worktrees | 给并行工作准备隔离的 Git 工作区 | 多任务同时修改同一仓库 | 不理解分支就直接使用 |
| Sandboxing | 限制 agent 可以访问和修改的范围 | 所有真实项目，尤其自动化 | 为图方便关闭隔离 |
| Configuration | 设置模型、权限、工具和行为默认值 | 希望跨会话保持一致 | 配置来源太多，不知道谁覆盖谁 |

## 四、适合纯新手的实际顺序

### 第一阶段：稳定完成小任务

1. 会说明目标、范围和验收标准
2. 会让 Claude 先检查再修改
3. 会看 `git diff`
4. 会撤回一次 checkpoint
5. 会维护最小 `CLAUDE.md`

### 第二阶段：减少重复劳动

1. 体验一个 slash command
2. 把成功重复的流程整理成 Skill
3. 用一个简单 Hook 自动运行确定性检查

### 第三阶段：接入和分工

1. 连接一个只读 MCP server
2. 把一个复杂任务拆给两个边界清楚的 subagents
3. 学习规划、权限和后台任务

### 第四阶段：团队化

1. 把稳定能力打包成 Plugin
2. 使用 CLI / print mode 做脚本和 CI
3. 制定团队级权限、安全和维护规则

## 五、学习时一直问自己的五个问题

每学一个新功能，都先问：

1. 它解决了我目前哪个真实问题？
2. 不使用它，我能不能先靠普通对话完成？
3. 它会读取或修改哪些东西？
4. 失败以后怎样撤回或恢复？
5. 我用什么证据判断它真的完成了？

如果第一个问题答不出来，可以先不学。学习 Claude Code 的目标不是收集功能，而是建立稳定、可检查、可复用的工作方式。
