## 第零部分:Claude Code vs Codex 全景对照

先别慌,你不需要记住每个细节。这张表是给你"在两套工具间来回切换不迷路"用的:

| 概念 | Claude Code | Codex | 一句话说明 |
|------|------------|-------|-----------|
| 项目指令文件 | `CLAUDE.md` | `AGENTS.md` | 都是给 AI 看的"项目约定" |
| 命令（固定流程） | `.claude/commands/*.md`（用 `/xxx` 触发） | `prompts/` 或自定义 prompt（用 `#xxx` 触发） | 你主动发起的快捷指令 |
| 技能（知识+方法） | `.claude/skills/`（一个文件夹,里面有 SKILL.md） | `skills/` 目录 | AI 根据任务自动加载的"操作手册" |

| 安装位置 | 项目级 `.claude/` + 用户级 `~/.claude/` | 类似（项目级 / 用户级） | 放项目里=这个项目用;放用户目录=所有项目用 |

> ⚠️ **重要提醒**:Codex 的机制更新很快,不同版本的路径和写法可能有差异。上表给你的是**概念对应关系**,帮你理解"原来是同一个东西"。真正动手配置时,以你装的 Codex 版本官方文档为准。

> 这篇笔记的**深度内容以 Claude Code 为准**(因为这个仓库教的就是它),Codex 部分给映射和思路,不逐字展开。

## 第一部分:Command / Skill / Subagent 三件套的本质区别

### 你最核心的误解:它们不是"一层升一层"

你猜的是:`command(MD 文件) → skill(文件夹) → subagent(MD 文件)` 层层递进。

**这个理解部分对,但方向错了。** 它们不是三个等级,而是**三种不同的封装形式**,解决三种不同的问题。它们不是"升级"关系,而是"并存、可以组合"的关系。

用一个办公室的比喻:

| 维度 | Command（命令） | Skill（技能） | Subagent（子代理） |
|------|----------------|--------------|-------------------|
| 类比 | **快捷键 / 常用话术** | **员工手册 / 操作规范** | **外包一个独立团队** |
| 谁触发 | **你**主动输入 `/xxx` | Claude 根据任务**自动加载** | 主 Claude **委派** |
| 是什么 | 一段固定流程的指令 | 知识+方法+步骤的打包 | 一个独立上下文的小助手 |
| 文件形式 | 单个 `.md` | **一个文件夹**（SKILL.md + 参考资料） | 单个 `.md` |

### 三个关键点

**① 你说"subagent 都是 MD 文件"——这个观察是对的。**

command 和 subagent 都是**单个 `.md` 文件**(frontmatter + 正文)。skill 是**一个文件夹**,因为它的"操作手册"（SKILL.md）经常需要配套参考资料(比如模板、示例代码),所以用一个文件夹装。

**② 三者的关系是"可组合",不是"可升级"。**

- **subagent 可以使用 skill**:比如一个"写汇报"的 subagent,自己不用带做 PPT 的知识,只要项目里有 PPT 这个 skill,它就能调用(后面第五部分详细讲)。
- **command 可以触发 subagent**:比如你可以写一条 `/review-code` 命令,命令内容就是"让主 Claude 调用 code-reviewer 审查当前改动"。

**③ 那"根据目的写一个东西",应该写成哪一种?**

| 你的目的 | 该用哪种 |
|----------|---------|
| "我每次都要手动做一遍这件事"（比如同步上游） | **Command**（你主动触发） |
| "希望 AI 遇到某类任务时,自动按规范来做"（比如写文档的格式） | **Skill**（AI 自动加载） |
| "希望把一个又大又杂的任务,交给一个专业的小助手单独做" | **Subagent**（主 Claude 委派） |

## 第二部分:Subagent 到底什么时候被调用?(你最困惑的点)

你说:"我不懂技术,只会提需求,它到底什么时候会自己去调 subagent?"

答案:**有两种触发方式,而且对你来说,第一种就够了。**

### 方式一:你主动委派(小白最实用)

你**直接点名**就行,不需要懂任何技术:

```
"用 code-reviewer 审查一下我最近的改动"
"把这份数据让 data-scientist 分析一下"
"让 documentation-writer 给我写个 README"
```

就这么简单。subagent 就是"一个专业员工",你只要说出员工名字 + 任务就行。**你不需要知道它内部怎么实现的。**

### 方式二:主 Claude 自动委派

主 Claude 会**看每个 subagent 的 `description`**(frontmatter 里的一句话描述),发现任务匹配,就自己决定调用。

**前提是 description 写得好。** 这正好对应教程里的"常见坑第 1 条:角色太模糊"——如果 description 写得太空,Claude 就不知道什么时候该派它上场。

**对你这样的新手,记住这个公式就够了:**

> description = 一句话说清楚"这个 agent 是干嘛的 + 什么时候适合用"

看两个真实例子(来自 `04-subagents/`):

```yaml
# code-reviewer 的 description
description: 资深代码审查专家。适合在代码修改后主动用于质量、安全和可维护性检查。

# performance-optimizer 的 description
description: 性能分析与优化专家。适合在写完或修改代码后主动用于识别瓶颈、提升吞吐和降低延迟。
```

注意"适合在**代码修改后**""适合在**写完或修改代码后**"这种写法——它明确告诉了 Claude **什么时候该用我**。这样当你写完功能说"帮我检查一下",Claude 就知道该派 code-reviewer 上场。

### 你不用担心的点

你说"我不懂技术,怕自己设计不好让 Claude 自动调用"——**这是把责任放错地方了。**

- **自动调用是 Claude 的职责,不是你的。** 你只需要把每个 subagent 的 description 写清楚(或者直接用现成的),剩下交给 Claude 判断。
- **你现在这个阶段,根本不用费心设计自动触发。** 先学会"点名派活"(方式一),等用熟练了,自然会理解什么时候写个 subagent 让 Claude 自动调。

## 第三部分:为什么"工具给太多"会失去隔离价值?(你不理解的点)

你说:"它不论工具给多少,只要单独分开做不就行吗?"

**不是的。** 这里有个关键逻辑:

### subagent 的核心价值是"专业分工"

| 价值 | 含义 |
|------|------|
| 上下文隔离 | 它的细节不污染主对话 |
| 专业分工 | 不同 agent 干不同的活 |
| 工具隔离 | **限制它能干什么** |

### 工具给太多为什么不好

如果一个 subagent 的工具给得太全(能读、能写、能跑、能改),它会变成:

> **一个"小号主 Claude"**——什么活都能干,主 Claude 就会把各种杂活都丢给它,它失去了"专业边界",而且**每一层都多烧一份 token**,资源浪费。

类比:你把一个"质量审查员"请进来,却给了他改代码的权限、管账的权限、发邮件的权限——那他到底是审查员还是全能杂工?边界一模糊,分工就散了。

### 正确做法:只给"这个角色完成任务需要"的工具

看真实例子:

```yaml
# code-reviewer——审查的人不该乱改代码,所以不给 Edit
tools: Read, Grep, Glob, Bash

# data-scientist——跑 SQL、读数据、写结果,就够了
tools: Bash, Read, Write

# performance-optimizer——要读、改、跑测试、搜代码
tools: Read, Edit, Bash, Grep, Glob
```

- 给太多 → 失去隔离价值(什么都能干,就不专业了)
- 给太少 → 干不了活(要改代码却不给 Edit,寸步难行)
- **刚刚好** → 只够完成这个角色的任务

## 第四部分:恢复已有 subagent(agentId / resume)

### 先肯定你理解对的部分

你那个"领导派标书给员工"的比喻,说的是**结果反馈**:

> 员工做完标书,不会把整个思考过程都搬回来,只把**成品(结果)**交给领导,领导拿着用就行。

这个理解**完全正确**。subagent 完成任务后,只把**最终报告**给主 Claude,不会把它的完整上下文倒回来。这就是"上下文隔离"的体现。

### 但 resume 是另一回事

resume 不是"把结果带回来",而是 **"保留这个员工自己的记忆,下次接着用同一个员工"**。

教程原文:

> 可恢复的 subagent 会返回 `agentId`。后续调用 Task tool 时,把这个值传给 `resume` 参数,就能保留原上下文继续执行。

**翻译成人话:**

- 普通情况下,subagent 跑完一次任务,它就"下班"了。下次再调,是**重新开一个什么都不记得的新员工**。
- 但有些时候,你想让这个员工**基于刚才的思路继续深入**(比如它分析到一半被打断,你想让它接着上次的分析往下走),这时候就用 `resume` + `agentId`,把**原来的那个员工**找回来,它还记得上次的一切。

### 类比对比

| 概念 | 你的"员工"比喻 | 实际含义 |
|------|---------------|---------|
| 结果反馈 | 员工把标书成品给领导 | subagent 把最终报告给主 Claude ✅(你理解对了) |
| resume + agentId | 领导喊回**同一个员工**,让他接着上次的思路干 | 保留 subagent 自己的上下文,下次接着用 |

### 一个容易混淆的坑

教程说"不要把它误写成主 session 的 `claude -r`":

- `claude -r <session>` 是恢复**主对话 session**(整个对话),不是 subagent
- resume 是**单独**把一个 subagent 的上下文找回来
- 两个不是一回事,别混

> 💡 **小白阶段先不用管 resume。** 它属于进阶用法。你现在只要知道:subagent 是"用完即走的独立员工",resume 是"想留住这个员工的记忆下次接着用"——有这个概念就行,实际用的时候再查。

## 第五部分:Subagent 会发现同一套 skills(你的理解正确!)

你问:"subagent 里面没写某个 skill,但项目里有,它能不能直接调用,不用重复放?"

**完全正确!** 教程原文:

> 从 `v2.1.133+` 开始,subagent 不再只看自己内嵌的那一小组能力。它会像主 session 一样,通过 Skill tool 发现:
> - 项目级 skills
> - 用户级 skills
> - plugin 提供的 skills

### 这意味着什么

**你不需要在每个 subagent 里重复塞公共 skill。**

举例(用你的 PPT 例子):

- 项目里已经有一个"做 PPT"的复杂 skill
- 你写一个"汇报专员"的 subagent
- 你**不需要**把做 PPT 的 skill 复制进这个 subagent
- 你只需要在 subagent 的正文里**提一句**"如果需要做 PPT,使用项目里的 PPT skill"
- 运行时,这个 subagent 会自己发现并调用它

### 一句话总结

> Skill 是"公共工具箱",Subagent 是"员工"。员工需要工具时,会自己去公共工具箱拿,不需要每个员工身上都背一套完整工具。

## 第六部分:嵌套分工(纠正你的"三级目录"误解)

你说你印象里是"一级目录、二级目录、三级目录,先读总的 agent.md,再一层层找更详细的"。

**这个理解部分对,但混了两个不同概念:**

### 概念一:spawn 嵌套深度(真正的"分工层级")

从 `v2.1.219` 起,subagent 默认可以再 spawn 子 subagent,默认深度 **3**。

类比:

```
总经理（主 Claude）
  └─ 部门经理（subagent A）
        └─ 组员（subagent A 再 spawn 的子 subagent）
```

这就是"嵌套分工"——一个 subagent 干不过来的大活,它自己再往下拆,叫帮手。每层都是**独立的上下文、独立的小助手**。

### 概念二:文件目录层级(定义放哪,不是调用层级)

教程里说的"嵌套 `.claude/agents/`":

> 从 `v2.1.178+` 起,如果 monorepo 里多个嵌套 `.claude/agents/` 都定义了同名 agent,Claude Code 会优先使用离当前工作目录最近的定义。

这是说**"同名 agent 定义放多个地方时,用离得近的"**——是"定义在哪生效"的问题,**不是**"一层层调用"的问题。

### "结合并发、权限和成本边界控制"是什么意思

教程那句话:

> 复杂任务可以利用嵌套分工,但仍要结合并发、权限和成本边界控制。

翻译成人话,嵌套分工不是无限拆,有三道闸:

| 控制 | 含义 | 默认值 |
|------|------|--------|
| **并发** | 同一时间最多跑几个 subagent | 20（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`） |
| **权限** | 限制某层能调用哪些子 agent | 用 `Agent(agent_type)` 语法限制 |
| **成本** | 每一层都烧 token,层数越深越贵 | 总 spawn 上限 200（`CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION`） |

**简单说:不是"能嵌套就拼命嵌套",而是"够用就好"。** 拆得太深,每一层都在花钱、花时间,还容易乱。复杂任务才值得拆,小事一层就够。

## 第七部分:安装 / 复制方式(你的理解正确)

你说:"subagent 是 MD 文件就复制文件,skill 是文件夹就复制文件夹,是不是?"

**完全正确。** 手动复制就行,不需要命令行工具。

### 安装 subagent(单个文件)

```bash
# 项目级(只在这个项目用)
cp 04-subagents/code-reviewer.md .claude/agents/

# 用户级(所有项目都能用)
mkdir -p ~/.claude/agents
cp 04-subagents/*.md ~/.claude/agents/
```

### 安装 skill(整个文件夹)

```bash
# 把整个 skill 文件夹复制过去
cp -r 03-skills/ppt-skill ~/.claude/skills/
```

### 两种位置的差别

| 位置 | 作用域 |
|------|--------|
| 项目级 `.claude/agents/` 或 `.claude/skills/` | 只在这个项目生效 |
| 用户级 `~/.claude/agents/` 或 `~/.claude/skills/` | 你所有项目都生效 |

> 也可以不手动复制——直接跟 Claude 说"创建一个负责安全审查的 subagent",它会帮你生成 `.claude/agents/<name>.md`。

## 第八部分:给小白用户的实操建议(核心!)

你说:"我知道原理,但实际操作时真不知道怎么拆,AI 对我来说就是个黑盒子。"

**这很正常,而且解决办法比你想的简单。** 给你一套"不用懂代码也能上手"的用法:

### ① 别想着设计"自动触发",先学会"点名派活"

```
"让 data-scientist 分析这份数据"
"用 secure-reviewer 检查一下有没有安全问题"
"让 documentation-writer 给我补个说明文档"
```

**这是你现阶段唯一需要会的用法。** 遇到哪类任务,就说让哪个 agent 做。就这么简单。

### ② 现成 agent 直接用,不用自己设计

`04-subagents/` 里有 9 个现成角色:

| 角色 | 用途 |
|------|------|
| `code-reviewer` | 代码审查 |
| `clean-code-reviewer` | Clean Code 角度审查 |
| `test-engineer` | 测试策略 |
| `documentation-writer` | 文档生成 |
| `secure-reviewer` | 安全检查 |
| `implementation-agent` | 功能实现 |
| `debugger` | 错误调试 |
| `data-scientist` | 数据分析与 SQL |
| `performance-optimizer` | 性能优化 |

```bash
cp 04-subagents/*.md .claude/agents/
```

复制完就能用。你**不需要**自己从头设计。

### ③ 想让某个 agent 被自动调用,只改 description 一句话

不用设计复杂逻辑。只要把 description 写成:

```
description: 负责 XXX 的专家。适合在【什么时机】主动用于【什么目的】。
```

写清楚"做什么 + 什么时候适合用",Claude 就会在任务匹配时自动调它。就这一句话的事。

### ④ 小白阶段先别碰嵌套

单层 subagent 足够你用了。等你能熟练"点名派活"、理解了隔离和分工,再研究嵌套深度、并发控制那些。

### ⑤ 用 Codex 时,套用同一套思路

你在 Codex 里的用法思路完全一样:

- **分工**:遇到大任务,让不同的"专业 agent"各干各的
- **专业**:每个 agent 只负责自己擅长的部分
- **隔离**:独立上下文,互不污染

具体文件路径以你的 Codex 版本文档为准,但"分工、专业、隔离"这三个思路是通用的。

## 收尾:一张图看懂全流程

```
你（用户）
  │ 提需求："帮我做个项目总结 PPT，顺便审查下最近的改动"
  ▼
主 Claude（总经理）
  │ 分析任务
  ├─► 发现要写 PPT → 加载 PPT skill（自动取用公共工具箱）
  ├─► 发现要审查代码 → 委派 code-reviewer subagent（专业员工）
  │        └─► code-reviewer 干完，只把审查报告交回来
  └─► 汇总结果，给你一个完整答复
```

- **Command** = 你按的快捷键(你主动)
- **Skill** = AI 自动翻的参考手册(自动)
- **Subagent** = 你/主 Claude 派出去的专业员工(委派)

三者**并存、可组合**,不是升级关系。记住这句话,你就把三件套串起来了。
