# 案例 02：手动练习导师

## 1. 原始表达特征

前面的典型要求是：

- “你不要给我操作，告诉我具体步骤，我手动做一遍。”
- “我用的是 PowerShell，不想用没见过的复杂写法。”
- “`cp` 能用就继续用，不要为了规范搞得很复杂。”
- “每一步解释是什么意思，做完怎样检查。”

真正目标不是拒绝 AI 帮助，而是让 AI 从“代办者”切换为“教练”。

## 2. 结构化后的任务定义

> 针对一个真实项目任务，只做必要的只读检查，不替用户执行修改；给出适用于 PowerShell 的逐步操作，每一步说明目的、预期结果、失败处理和检查点，等待用户亲手完成。

## 3. 原始表达容易遗漏什么

- AI 是否允许做只读检查；
- 一次给全部步骤，还是一步一步等待反馈；
- 命令失败时怎样诊断；
- 哪些步骤会产生真实副作用；
- 是否需要备份或查看 Git 状态；
- PowerShell 简写和完整命令怎样选择。

## 4. 为什么先做成提示词

这个工作方式可以用于安装 Skill、学习 Git、复制文件等不同任务。它主要改变 AI 的协作模式，目前不需要固定模板或脚本，所以提示词最合适。

## 5. 五张需求卡

### 触发卡

用户明确说“不要替我操作”“我要手动练习”“只给步骤”时使用。

### 输入卡

- 要完成的任务；
- 当前项目路径；
- 使用的终端；
- 是否允许 AI 做只读检查；
- 希望一步一步还是一次看完整流程。

### 流程卡

1. 只读确认环境；
2. 说明目标和风险；
3. 给最短可用命令；
4. 解释命令；
5. 给预期输出和检查命令；
6. 失败时先诊断，不擅自代做。

### 输出卡

- 开始前检查；
- 编号步骤；
- 每一步的命令、解释、预期结果；
- 风险提醒；
- 最终验收；
- 最短操作清单。

### 边界与验收卡

- 不执行修改命令；
- 不自动提交或推送；
- 简单 `cp` 能用时不强制写成长命令；
- 明确区分 PowerShell 命令和 Skill 内部 Bash 工具；
- 用户应能独立重复一遍。

## 6. 怎样与 AI 一起创建这条提示词

```text
我希望 AI 在学习任务中做教练，不替我执行。请先帮我定义：允许 AI 做哪些只读检查、每一步应该解释什么、怎样处理 PowerShell 与 Bash 差异、怎样设置检查点。先不要写最终提示词。
```

确认后继续：

```text
现在把这些要求写成一条平台通用提示词。默认使用 PowerShell，简单命令优先；每一步必须包含目的、命令、预期结果和失败处理，并明确禁止代替用户执行修改。
```

## 7. 使用方式

把 `可直接使用的提示词.md` 中的任务、路径和协作节奏替换后使用。如果用户要边做边反馈，选择“逐步模式”；如果想先看全貌，选择“完整清单模式”。

## 8. Codex 迁移说明

这是协作模式提示词，可直接用于 Codex。Codex 能进行只读检查，但提示词明确要求不执行修改；如果以后希望长期固定该偏好，更适合写进个人指导或 `AGENTS.md`，而不是必须做成 Skill。
