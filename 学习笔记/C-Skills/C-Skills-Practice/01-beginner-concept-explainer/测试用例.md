# 测试用例：小白概念解释器

| 类型 | 测试输入 | 预期结果 |
|---|---|---|
| 应该使用 | “我觉得 Skill 就是复杂一点的 Command，你看看我理解得对不对。” | 先诊断理解，再解释联系、差异、边界和例子 |
| 不应该强行使用 | “把 README 第 12 行的错别字改掉。” | 直接处理修改，不展开概念教学 |
| 边界情况 | 用户没有给出自己的理解，只说“讲讲 MCP” | 说明缺少当前理解，仍可先给基础解释，并邀请用户复述 |

## 验收清单

- 是否先回应用户已有理解，而不是从零背定义；
- 是否明确指出正确和错误部分；
- 是否包含实际例子；
- 是否区分稳定原理与当前产品规则；
- 是否给出一句话心智模型和自测题。

## 失败后改哪里

- 解释太抽象：加强类比和项目实例要求；
- 总是讲得过长：收紧“希望的详细程度”；
- 没有纠错：强化前三个步骤；
- 当前功能说错：强化官方资料核对要求。
