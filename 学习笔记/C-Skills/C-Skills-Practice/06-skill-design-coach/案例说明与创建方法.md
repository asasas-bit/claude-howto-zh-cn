# 案例 06：Skill 设计教练

## 1. 原始表达特征

核心困惑反复表现为：

- “文件结构我都看得懂，但让我自己创建就不知道怎么下手。”
- “我可以让 AI 创建，但它给我什么我就只能接受什么。”
- “我希望像老板一样，不亲手做所有细节，但知道怎样定义和验收。”
- “我不想一开始就创建很多没用的目录。”

这说明真正缺少的是 Skill 设计决策，而不是 Markdown 输入能力。

## 2. 结构化后的任务定义

> 通过五张需求卡澄清目标，再根据重复度、确定性、触发时机、资源依赖和风险选择 Prompt、Skill、Script、Hook 或 MCP；分需求、结构、创建、解释四道闸门推进；未经确认不创建文件，完成后用三类场景验收。

## 3. 为什么是复杂 Skill

- 需要多轮交互；
- 需要保存稳定的决策规则；
- 需要模板帮助用户表达；
- 需要把设计与执行分开；
- 需要测试矩阵和失败定位；
- 可以用于继续创建其他 Skills，属于“元工作流”。

## 4. 五张需求卡

### 触发卡

当用户想创建、改造或审查 Skill，但需求仍模糊，或不知道需要哪些资源时使用。

### 输入卡

- 重复发生的真实任务；
- 具体使用例子；
- 目标平台和安装范围；
- 风险和需要确认的操作；
- 现有提示词、Command 或 Skill。

### 流程卡

1. 访谈并完成五张卡；
2. 判断正确载体；
3. 设计最小结构；
4. 解释每个文件存在理由；
5. 用户确认后创建；
6. 解释设计；
7. 运行三类测试并迭代。

### 输出卡

- 五张需求卡；
- 载体选择与理由；
- 最小目录；
- 创建提示词或完成文件；
- 测试矩阵；
- 迭代建议。

### 边界与验收卡

- 设计阶段不修改文件；
- 不为完整而创建空目录；
- 高风险操作必须显式确认；
- 每个资源都能回答“解决哪个真实问题”；
- 新会话测试能够通过。

## 5. 怎样与 AI 一起创建

本 Skill 自己就体现四道闸门：先访谈、再设计、再创建、最后解释与测试。第一次练习时，可以先只执行前两道闸门，自己判断方案后再继续。

## 7. Codex 迁移说明

- Codex 版本保留五张卡、资源选择规则和测试模板；
- frontmatter 只使用 `name` 与完整 `description`；
- 将模板放在 `assets/`，决策规则放在 `references/`；
- 可使用 Codex 自带的 Skill 创建工作流生成规范目录和校验元数据；
- 个人安装到 `$CODEX_HOME/skills/skill-design-coach/`；
- 不复制 Claude 专属 `argument-hint` 等字段。
