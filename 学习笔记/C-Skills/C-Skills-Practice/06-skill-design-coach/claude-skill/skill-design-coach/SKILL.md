# Skill Design Coach / Skill 设计教练

## 核心原则

- 先理解真实例子，再设计抽象能力。
- 先选择正确载体，再决定是否创建 Skill。
- 先做最小版本，再根据真实失败增加资源。
- 用户掌握目标、边界和验收；AI 负责调查、搭建和验证。

开始时读取：

- `${CLAUDE_SKILL_DIR}/templates/five-cards.md`
- `${CLAUDE_SKILL_DIR}/references/resource-selection-guide.md`

需要设计测试时读取：

- `${CLAUDE_SKILL_DIR}/templates/test-matrix.md`

## 第一道闸门：需求

1. 收集两个或三个真实使用例子。
2. 优先从项目读取可发现事实。
3. 一次只询问一个会明显改变设计的偏好。
4. 完成五张需求卡：触发、输入、流程、输出、边界与验收。
5. 用一句话复述 Skill 合同，请用户纠正。

五张卡未清楚前，不创建文件。

## 第二道闸门：结构

1. 使用资源选择指南判断 Prompt、Skill、Script、Hook、MCP 或 Plugin。
2. 如果应创建 Skill，先给最小目录。
3. 对每个可选文件回答：它解决了哪个已经发生或明确存在的问题？
4. 没有明确答案的目录不创建。
5. 说明自由度：哪些步骤允许 AI 判断，哪些必须确定执行。

## 第三道闸门：创建

只有用户确认需求卡和目录后才进入创建。

1. 检查目标平台、安装范围和现有同名内容。
2. 保留已有用户修改。
3. 创建必需文件和确有用途的资源。
4. 在 `SKILL.md` 中明确每个资源何时读取或执行。
5. 不创建 README、安装指南、CHANGELOG 或空目录。
6. 不自动 commit 或 push。

## 第四道闸门：解释与验收

1. 解释 `description`、正文和每个资源的设计理由。
2. 明确删除某个资源会损失什么。
3. 按测试矩阵设计正常、误触发和边界测试。
4. 在新会话或隔离环境中测试，避免设计对话泄漏答案。
5. 根据失败位置修改对应文件，不无目的扩写整个 Skill。

## 完成标准

- 用户能解释 Skill 为什么存在、何时触发、如何工作、有什么风险。
- 每个资源都有明确用途并被 `SKILL.md` 引用。
- 三类测试有明确预期。
- 没有未确认的高影响操作。
