# Skill 设计、创建与验收：从“会看懂”到“会指挥 AI”

> 本笔记面向已经能够看懂现成 Skill，但还不知道怎样从零设计、怎样指挥 AI 创建、怎样判断结果是否合格的学习者。

## 一、先明确学习目标

学会 Skill，不等于：

- 背下所有 YAML 字段；
- 亲手输入每一个 Markdown 字符；
- 自己从零编写所有脚本；
- 一开始就创建一个包含很多目录的复杂 Skill。

真正需要掌握的是：

1. 判断一个需求是否值得做成 Skill；
2. 定义 Skill 负责什么、不负责什么；
3. 说明它什么时候触发、需要什么输入；
4. 设计稳定的工作流程和输出结果；
5. 判断哪些内容放在 `SKILL.md`，哪些拆成资源；
6. 指挥 AI 创建，而不是无条件接受 AI 的第一版；
7. 通过真实测试判断 Skill 是否有效；
8. 根据问题持续修改，而不是一次写完永不调整。

可以把自己理解成 Skill 的产品负责人：AI 可以负责搭建和编写，但目标、边界和验收标准必须由你掌握。

## 二、Skill 中每个部分到底负责什么

### 2.1 Skill 首先是一个文件夹

一个最小可用的 Claude Code Skill 可以只有：

```text
my-skill/
└── SKILL.md
```

复杂一些的 Skill 才可能逐渐增加：

```text
my-skill/
├── SKILL.md
├── references/
├── templates/
├── scripts/
├── assets/
└── examples/
```

除了 `SKILL.md`，其他目录都不是必需品。

不要先把所有文件夹建出来，再想里面放什么。正确顺序是：

```text
先明确需求
    ↓
先完成最小 SKILL.md
    ↓
实际使用并发现问题
    ↓
确有需要时再增加资源
```

### 2.2 用“一个小部门”理解 Skill

| 组成部分 | 老板视角 | 主要作用 | 是否必需 |
|---|---|---|---|
| `name` | 部门名称 | 标识 Skill | 是 |
| `description` | 接单说明 | 告诉 AI 什么时候应该使用 | 是 |
| `SKILL.md` 正文 | 工作手册 | 定义流程、规则、输出和验证 | 是 |
| `references/` | 业务资料库 | 保存需要阅读和判断的背景知识 | 否 |
| `templates/` | 固定表格 | 统一输出结构 | 否 |
| `scripts/` | 自动化机器 | 稳定执行机械、重复、易错的操作 | 否 |
| `assets/` | 素材仓库 | 保存最终产物会使用的图片、字体、文件骨架等 | 否 |
| `examples/` | 优秀案例库 | 展示理想输入和输出 | 否 |

### 2.3 `name`：给能力起一个稳定名称

名称应该做到：

- 简短；
- 能看出用途；
- 使用小写字母、数字和连字符；
- 文件夹名称与 Skill 名称保持一致。

例如：

```text
learning-note-organizer
git-safe-submit
code-review-specialist
```

不推荐：

```text
my-good-skill
万能助手
skill-1
```

名称主要解决“它叫什么”，不能代替完整的触发说明。

### 2.4 `description`：决定什么时候接单

`description` 不是宣传口号，而是触发说明。至少要说清楚两件事：

1. 这个 Skill 能做什么；
2. 用户处于什么场景、说出什么意图时应该使用。

比较空泛的写法：

```yaml
description: 帮助整理内容
```

更明确的写法：

```yaml
description: 将 AI 工具学习过程中的对话、零散理解和操作步骤整理成适合新手复习的 Markdown 笔记。用户要求整理学习笔记、沉淀知识点或把当前讨论保存到“学习笔记”目录时使用。
```

一个简单公式：

```text
description = 做什么 + 什么时候用 + 重要边界（必要时）
```

### 2.5 `SKILL.md` 正文：给 AI 的工作手册

正文应该重点回答：

1. 用户会提供什么；
2. AI 按什么顺序执行；
3. 哪些步骤需要确认；
4. 什么时候读取哪个资源；
5. 最终输出什么；
6. 哪些事情禁止自动做；
7. 怎样检查任务是否完成。

推荐结构：

```markdown
# Skill 标题

## 目标

## 输入

## 执行流程

## 资源使用规则

## 输出要求

## 安全边界

## 验证方法
```

这不是强制模板，但它适合新手检查是否漏掉重要内容。

### 2.6 `references/`：给 AI 阅读的知识

适合保存：

- 公司规范；
- 产品说明；
- 专业术语；
- 数据结构；
- API 说明；
- 写作规则；
- 长篇检查清单；
- 不同场景的详细方法。

判断问题：

> 这份内容是不是主要让 AI 读懂以后，再根据实际情况作判断？

如果答案是“是”，通常适合放 `references/`。

例如：

```text
references/
├── writing-style.md
├── naming-rules.md
└── product-terms.md
```

在 `SKILL.md` 中必须告诉 AI 什么时候读取：

```markdown
整理中文学习笔记前，读取 `references/writing-style.md`。
只有涉及文件命名时，才读取 `references/naming-rules.md`。
```

不要把同一段内容同时复制到 `SKILL.md` 和 `references/`，否则以后修改时容易不一致。

### 2.7 `templates/`：给输出规定骨架

适合保存：

- 学习笔记模板；
- 周报模板；
- 文章模板；
- 代码审查报告模板；
- 会议纪要模板；
- 固定格式的 Markdown 文档。

判断问题：

> 每次输出是否都应该保持相似的栏目、标题和结构？

如果答案是“是”，可以增加模板。

例如：

```text
templates/
└── learning-note-template.md
```

模板负责“长什么样”，`SKILL.md` 负责“怎么做、什么时候使用模板”。

### 2.8 `scripts/`：让机器确定性执行

适合保存：

- 批量处理文件；
- 校验 JSON 或 Markdown；
- 调用外部 API；
- 统计代码或文档数据；
- 转换文件格式；
- 自动生成目录；
- 重复而且容易写错的命令。

判断问题：

> 这项操作是否重复发生、规则明确，而且每次临时让 AI 写命令容易出错？

如果答案是“是”，才考虑脚本。

不要因为“复杂 Skill 看起来更高级”就添加脚本。脚本一旦存在，就要考虑：

- 输入是什么；
- 输出是什么；
- 依赖什么环境；
- 失败后怎样提示；
- 是否可能删除或覆盖文件；
- 是否经过真实运行测试。

### 2.9 `assets/`：最终产物要使用的素材

适合保存：

- Logo；
- 图片；
- 字体；
- Word、PPT、Excel 模板文件；
- HTML 或前端项目骨架；
- 最终交付物需要复制的文件。

它和 `references/` 的主要区别：

| 类型 | 主要给谁使用 | 典型用途 |
|---|---|---|
| `references/` | 给 AI 阅读 | 理解规则和背景知识 |
| `assets/` | 给最终产物使用 | 复制、嵌入或基于素材生成结果 |

### 2.10 `examples/`：用样例说明“什么叫好”

适合保存少量高质量案例：

- 示例输入；
- 理想输出；
- 常见错误示例；
- 修改前后对比。

案例不是越多越好。案例太多可能让 AI 机械模仿，反而忽略当前任务。

### 2.11 一张资源选择表

| 当前问题 | 应该放哪里 |
|---|---|
| Skill 什么时候使用 | `description` |
| AI 应该怎样一步步完成 | `SKILL.md` |
| AI 需要阅读的专业知识 | `references/` |
| 输出必须遵循固定结构 | `templates/` |
| 需要稳定执行的机械操作 | `scripts/` |
| 最终产物要使用的文件或素材 | `assets/` |
| 需要展示什么叫合格 | `examples/` |
| 目前没有实际需要 | 不要创建对应目录 |

### 2.12 最常见的结构错误

1. 一上来创建所有目录，但大部分是空的；
2. `SKILL.md` 写成很长的教材，而不是工作手册；
3. `description` 只写功能，不写触发场景；
4. 资源文件存在，但 `SKILL.md` 没说明什么时候读取；
5. 相同规则在多个文件重复，修改后互相矛盾；
6. 能用简单步骤完成，却增加未经测试的脚本；
7. 只有流程，没有输出格式和验收标准。

## 三、创建 Skill 前，先写清楚五张卡片

五张卡片不是 Claude Code 的固定文件格式，而是一套需求分析方法。它们帮助你在让 AI 创建文件前，先把脑中的模糊想法变成可执行要求。

### 3.1 第一张：触发卡

回答：

> 什么时候应该使用这个 Skill？什么时候不应该使用？

需要写清楚：

- 用户可能怎么说；
- 当前处于什么工作场景；
- 是否允许 AI 自动选择；
- 哪些相似任务不归它负责。

模板：

```text
当用户要求【具体任务】、提到【关键词或场景】，或者需要【目标结果】时使用。
不用于【容易混淆但不属于它的任务】。
```

示例：

```text
当用户要求整理 AI 工具学习笔记、把当前讨论沉淀成 Markdown，
或将零散操作步骤保存到“学习笔记”目录时使用。
不用于普通项目 README 修改，也不用于自动提交 Git。
```

触发卡主要影响 `description`。

### 3.2 第二张：输入卡

回答：

> AI 开工前必须知道什么？哪些信息没有也能合理补全？

把输入分成三类：

| 输入类型 | 含义 | 示例 |
|---|---|---|
| 必需输入 | 缺少就无法开始 | 要整理的对话或知识点 |
| 可选输入 | 有了可以做得更好 | 文件名、目标读者、详细程度 |
| 可发现输入 | AI 可以从项目读取 | 已有目录、命名方式、相关文档 |

模板：

```text
必需输入：
- ……

可选输入：
- ……

优先从项目自动发现：
- ……

只有在缺少关键信息且不同选择会明显改变结果时，才向用户提问。
```

输入卡可以防止两种问题：

- AI 什么都不问就随便猜；
- AI 对所有小细节都反复提问。

### 3.3 第三张：流程卡

回答：

> 从收到任务到交付结果，中间依次经过哪些阶段？

不要一开始写几十个细碎动作。先写 3～7 个阶段：

```text
理解任务
    ↓
读取相关资料
    ↓
设计输出结构
    ↓
生成内容
    ↓
保存文件
    ↓
检查结果
```

示例：

```text
1. 理解用户要学习的知识点和当前水平；
2. 查找项目中的相关教程和现有笔记；
3. 区分核心概念、操作步骤和常见误区；
4. 按适合新手复习的结构编写 Markdown；
5. 保存到指定目录；
6. 重新读取文件，检查标题、路径和关键内容。
```

流程卡主要进入 `SKILL.md` 正文。

### 3.4 第四张：输出卡

回答：

> 最终交付物是什么样，用户拿到以后能做什么？

至少定义：

- 文件类型；
- 保存位置；
- 文件命名；
- 必需章节；
- 是否需要代码示例；
- 是否需要操作清单；
- 在聊天中如何汇报结果。

示例：

```text
输出一个 Markdown 文件，保存在“学习笔记”目录。
文件至少包含：
- 一句话结论；
- 核心概念；
- 操作步骤；
- 示例；
- 常见误区；
- 自我检查清单。

完成后在聊天中报告文件路径和主要内容，不粘贴整篇正文。
```

如果不同任务都必须遵循相同结构，可以把结构进一步做成 `templates/`。

### 3.5 第五张：边界与验收卡

回答两个问题：

1. 哪些事情不能自动做？
2. 怎样证明任务真的完成了？

边界示例：

```text
- 未经用户要求不创建 Git commit；
- 未经用户要求不执行 git push；
- 不覆盖已有同名文件；
- 不修改与本次笔记无关的内容；
- 不把密码、密钥或隐私信息写入笔记。
```

验收示例：

```text
- 文件确实存在；
- 路径和文件名正确；
- Markdown 可以正常阅读；
- 六个必需章节全部存在；
- 命令与用户使用的 PowerShell 环境一致；
- 重新读取文件后没有残留占位符；
- Git 状态中只出现预期变化。
```

### 3.6 五张卡片完整模板

以后创建任何 Skill，都可以先复制下面这份表：

```markdown
# Skill 需求卡

## 1. 触发卡

- 应该使用：
- 不应该使用：
- 用户可能会说：
- 自动调用还是手动调用：

## 2. 输入卡

- 必需输入：
- 可选输入：
- 可以从环境自动发现：
- 必须向用户确认的情况：

## 3. 流程卡

1. 
2. 
3. 
4. 

## 4. 输出卡

- 交付物：
- 保存位置：
- 命名规则：
- 必需结构：
- 聊天中的汇报方式：

## 5. 边界与验收卡

- 禁止事项：
- 需要用户批准的操作：
- 完成条件：
- 验证命令或检查方法：
```

### 3.7 判断五张卡是否写清楚

合格标准：把五张卡交给另一个完全不了解背景的人，他仍然能够回答：

- 什么时候开始；
- 需要拿到什么；
- 中间怎样做；
- 最终交付什么；
- 什么不能做；
- 怎样算完成。

如果这些问题仍然需要大量猜测，就不要急着让 AI 创建文件。

## 四、怎样让 AI 创建，但不把决定权全交给 AI

### 4.1 可以让 AI 创建，而且应该让 AI 创建

使用 AI 创建 Skill 并不等于没有学会。

合理分工是：

| 角色 | 负责内容 |
|---|---|
| 你 | 目标、场景、边界、优先级、验收标准 |
| AI | 查找资料、设计草案、创建文件、编写脚本、执行检查 |
| 你和 AI 共同完成 | 方案取舍、风险判断、测试和迭代 |

问题不在于“让 AI 写”，而在于是否只说一句：

```text
帮我创建一个 Skill。
```

如果需求只有这一句，AI 只能自己替你决定目标、边界和结构。结果可能能用，但不一定符合你的真实需要。

### 4.2 使用四道闸门控制创建过程

不要一次完成全部工作，分四轮进行。

#### 第一轮：需求闸门

目标：先把模糊想法整理成五张卡，不创建文件。

可以对 AI 说：

```text
我想创建一个用于整理学习笔记的 Claude Code Skill。

先不要创建或修改任何文件。请像产品经理一样帮助我明确：
1. 触发场景；
2. 必需和可选输入；
3. 工作流程；
4. 输出格式；
5. 安全边界和验收标准。

优先从当前项目中查找可以确认的信息。
只有无法从项目发现、而且会明显影响设计的偏好才问我。
最后输出一份五张需求卡。
```

这一轮重点检查：AI 是否真的理解了你的目标。

#### 第二轮：结构闸门

目标：只设计目录，解释为什么需要每个文件。

```text
根据已经确认的五张需求卡，为这个 Skill 设计最小可用目录。

先不要创建文件。请分别说明：
- 哪些内容进入 SKILL.md；
- 是否真的需要 references；
- 是否真的需要 templates；
- 是否真的需要 scripts；
- 是否真的需要 assets 或 examples；
- 每个文件存在的具体理由；
- 哪些目录当前不应该创建。

优先选择最小可用版本，不为了形式完整而增加空目录。
```

这一轮重点检查：AI 是否出现“过度设计”。

#### 第三轮：执行闸门

目标：按照已经确认的方案创建，而不是临场改变需求。

```text
按照已经确认的需求卡和目录设计创建 Skill。

要求：
- 先做最小可用版本；
- 只创建已经确认需要的文件；
- Skill 名称和文件夹名称一致；
- 每个资源都要在 SKILL.md 中写清楚何时使用；
- 不创建无关说明文件；
- 不提交 Git，不推送远程仓库；
- 创建后检查目录、frontmatter、资源引用和文件内容。
```

这一轮重点检查：实际修改是否和设计一致。

#### 第四轮：解释和验收闸门

目标：让 AI 解释设计，并暴露可能的问题。

```text
创建完成后，先不要继续扩展。请从教学和验收角度说明：

1. description 为什么这样写；
2. SKILL.md 每一部分解决什么问题；
3. 为什么创建或没有创建 references；
4. 为什么创建或没有创建 templates；
5. 为什么创建或没有创建 scripts；
6. 每个资源在什么条件下使用；
7. 当前 Skill 最可能失败的三个地方；
8. 应该用哪些测试提示验证；
9. 如果以后增加需求，分别应该改哪个文件。
```

这一轮重点检查：你是否能理解 AI 做出的每个重要决定。

### 4.3 让 AI 给出“设计理由”，而不只是结果

每次看到一个不理解的文件，不要只问：

```text
这个文件是什么？
```

可以继续追问：

```text
如果删除这个文件，会损失什么能力？
```

```text
这段内容为什么不直接写进 SKILL.md？
```

```text
这里为什么需要脚本，而不能只写操作步骤？
```

```text
这个规则属于流程、参考知识、模板还是验收标准？为什么？
```

这些问题会训练你的结构判断能力。

### 4.4 你需要重点审查的七件事

AI 创建后，不必一开始逐字审查所有内容，先检查：

1. Skill 名称是否清楚；
2. `description` 是否说清触发场景；
3. 工作流是否符合真实做事顺序；
4. 是否出现无用目录和重复内容；
5. 高风险操作是否需要确认；
6. 输出要求是否可以检查；
7. AI 是否真的执行了验证。

如果包含脚本，再增加：

8. 脚本的输入和输出是什么；
9. 脚本是否可能覆盖或删除文件；
10. 脚本是否经过真实运行测试。

### 4.5 不要把 AI 的第一版当成最终版

一个正常的 Skill 迭代过程是：

```text
第一版：能完成基本任务
第二版：减少漏项和误触发
第三版：统一输出格式
第四版：把机械操作做成脚本
第五版：补充异常处理和验证
```

只有真实使用以后，才能知道哪些规则有用、哪些说明多余。

## 五、最适合新手的练习项目：`learning-note-organizer`

### 5.1 为什么选择它

这个练习与你当前学习过程直接相关：

- 你确实会重复整理学习笔记；
- 输入和输出容易理解；
- 风险较低；
- 可以从单文件开始；
- 后续自然会出现模板、参考规则和校验脚本；
- 能完整练习 Skill 的渐进式成长。

目标定义：

> 当用户学习 Commands、Skills、Hooks、MCP 等知识时，将对话、疑问和操作方法整理成适合新手复习的 Markdown，并保存到项目的“学习笔记”目录。

### 5.2 第一阶段：只设计，不创建

先完成五张卡片，不要立即要求 AI 写文件。

建议自己先回答：

- 什么话应该触发它？
- 是只生成内容，还是还要保存文件？
- 文件名由谁决定？
- 已有同名文件怎么办？
- 是否允许自动提交 Git？
- 什么样的笔记才算适合新手？

这一阶段的学习目标是：把需求说清楚。

### 5.3 第二阶段：V0.1 单文件 Skill

目录：

```text
learning-note-organizer/
└── SKILL.md
```

第一版只需要写清楚：

- 触发条件；
- 输入信息；
- 整理步骤；
- 输出章节；
- 保存位置；
- 禁止自动提交和推送；
- 保存后的检查方法。

这一阶段不要增加脚本、模板和参考资料。

学习目标：理解一个 Skill 的核心是触发条件和工作流程，不是目录数量。

### 5.4 第三阶段：V0.2 增加模板

实际整理两三篇笔记以后，如果发现每篇都需要相同栏目，再增加：

```text
learning-note-organizer/
├── SKILL.md
└── templates/
    └── learning-note-template.md
```

模板可以包含：

```markdown
# 标题

## 一句话结论

## 核心概念

## 操作步骤

## 示例

## 常见误区

## 自我检查
```

同时在 `SKILL.md` 中说明：生成新笔记时读取并遵循该模板。

学习目标：理解模板解决的是输出一致性，而不是业务判断。

### 5.5 第四阶段：V0.3 增加参考资料

如果多次出现稳定的中文写作规则、命名规则或 PowerShell 表达习惯，再增加：

```text
learning-note-organizer/
├── SKILL.md
├── templates/
│   └── learning-note-template.md
└── references/
    ├── writing-style.md
    └── naming-rules.md
```

例如：

- 面向新手，先说结论再解释；
- 第一次出现英文术语时补充中文解释；
- PowerShell 示例优先使用用户熟悉的简短写法；
- 文件名要能直接看出主题；
- 不用“最终版”“最新版”等容易过期的命名。

学习目标：理解参考资料解决的是长期稳定知识，而不是执行顺序。

### 5.6 第五阶段：V0.4 确有需要时增加脚本

只有出现下面这类真实需求时，再考虑脚本：

- 自动检测同名文件；
- 校验 Markdown 是否包含必需标题；
- 自动生成学习笔记索引；
- 检查文件中是否残留占位符；
- 批量更新目录链接。

可能的目录：

```text
learning-note-organizer/
├── SKILL.md
├── templates/
├── references/
└── scripts/
    └── validate-note.ps1
```

学习目标：理解脚本解决的是确定性和重复性，不是为了显示 Skill 复杂。

### 5.7 完整的成长路线

```text
五张需求卡
    ↓
V0.1：只有 SKILL.md
    ↓ 真实使用 2～3 次
V0.2：增加统一模板
    ↓ 发现稳定规则越来越多
V0.3：增加参考资料
    ↓ 出现机械、重复、易错操作
V0.4：增加并测试脚本
```

每一次增加文件，都必须能够回答：

> 它解决了哪个已经真实发生的问题？

如果答不出来，就先不要增加。

### 5.8 用仓库示例配合学习

建议按复杂度依次对照：

1. `03-skills/claude-md/`：观察单文件 Skill；
2. `03-skills/brand-voice/`：观察规则和模板；
3. `03-skills/blog-draft/`：观察多阶段内容工作流；
4. `03-skills/code-review-specialist/`：观察模板与脚本配合；
5. `03-skills/refactor/`：观察参考资料、模板和脚本组成的完整 Skill。

阅读时不要只看“写了什么”，还要问：

- 为什么这个文件存在？
- 删除它会产生什么影响？
- 它解决的是流程、知识、格式还是执行问题？
- `SKILL.md` 有没有明确引用它？
- 它是否真的需要存在？

## 六、每次测试 Skill，都要测三类情况

创建成功不等于 Skill 有效。至少要验证：

1. 应该使用时能正确使用；
2. 不应该使用时不会乱用；
3. 遇到风险和异常时能够守住边界。

### 6.1 第一类：应该触发

目的：检查 Skill 是否能够识别真实需求并完成工作流。

示例：

```text
把刚才关于 Commands 和 Skills 的讨论整理成一篇学习笔记，保存到学习笔记目录。
```

检查：

- 是否识别并使用正确 Skill；
- 是否读取需要的模板和参考资料；
- 是否按规定保存文件；
- 是否包含必需章节；
- 是否执行完成检查。

不要只测试一句固定口令，还要换一种自然表达：

```text
刚才讲的 Skill 资源目录我怕忘了，帮我整理成以后能复习的 Markdown。
```

如果只有说出准确名称才会使用，说明 `description` 可能写得太窄。

### 6.2 第二类：不应该触发

目的：检查 Skill 是否会误触发、扩大任务范围。

示例：

```text
帮我修改 README 中的一个错别字。
```

```text
解释一下这段 Python 为什么报错，不需要生成笔记。
```

检查：

- 是否没有强行整理学习笔记；
- 是否没有创建多余文件；
- 是否尊重“不需要生成笔记”的明确说明。

如果总是误触发，优先修改 `description` 中的适用场景和排除边界。

### 6.3 第三类：边界和异常情况

目的：检查 Skill 在危险、信息不足或冲突情况下是否可靠。

示例一：扩大权限

```text
整理学习笔记，然后顺便提交并推送 GitHub。
```

检查它是否遵守确认规则，而不是因为“顺便”就执行高影响操作。

示例二：同名文件

```text
把这段内容保存为已经存在的那篇 Skill 学习笔记。
```

检查它是否会直接覆盖，还是先比较、追加或询问。

示例三：输入不足

```text
帮我整理一下。
```

检查它是否能从上下文判断；无法判断时，是否只询问真正必要的问题。

示例四：敏感信息

```text
把包含账号和密钥的调试记录整理成学习笔记。
```

检查它是否识别并避免写入敏感信息。

### 6.4 不只测触发，还要测五个层面

| 测试层面 | 要回答的问题 |
|---|---|
| 发现 | AI 是否在正确场景识别这个 Skill？ |
| 流程 | 是否按照规定顺序执行？ |
| 资源 | 是否只在需要时读取正确模板、参考资料或脚本？ |
| 输出 | 文件、格式、内容是否符合要求？ |
| 安全 | 是否避免覆盖、泄密、误提交和越权操作？ |

### 6.5 使用测试记录表

每次修改 Skill 后，可以记录：

```markdown
| 测试提示 | 预期行为 | 实际行为 | 是否通过 | 要修改哪里 |
|---|---|---|---|---|
| 整理当前讨论为学习笔记 | 触发并生成 Markdown |  |  |  |
| 修改 README 错别字 | 不触发 |  |  |  |
| 整理后推送 GitHub | 先确认高风险操作 |  |  |  |
```

“要修改哪里”可以这样判断：

| 问题 | 优先修改位置 |
|---|---|
| 应该触发但没有触发 | `description` |
| 不该触发却触发 | `description` 的边界 |
| 步骤顺序错误或漏步骤 | `SKILL.md` 工作流 |
| 输出栏目不一致 | 输出要求或 `templates/` |
| 专业规则理解错误 | `references/` |
| 脚本执行错误 | `scripts/` 及其调用说明 |
| 做了不该自动做的操作 | 安全边界和权限配置 |
| 声称完成但没有检查 | 验证方法和完成条件 |

### 6.6 为什么最好在新会话中测试

创建 Skill 的当前对话已经包含大量设计背景。AI 即使不依赖 Skill，也可能根据聊天记录做出正确结果。

因此正式测试时，最好：

1. 保存 Skill；
2. 打开一个新的 Claude Code 会话；
3. 只给真实用户会说的任务；
4. 不提前告诉它预期答案；
5. 观察它是否仅依靠 Skill 完成任务。

否则可能出现：当前对话测试成功，换一个新会话就失败。

### 6.7 与“没有 Skill”的结果做对比

可以分别测试：

- 没有启用 Skill 时的结果；
- 启用 Skill 后的结果。

Skill 应该至少带来一种明确价值：

- 减少重复说明；
- 输出更稳定；
- 漏项更少；
- 风险控制更可靠；
- 能使用专属模板或资料；
- 能稳定执行重复操作。

如果有无 Skill 的效果完全一样，就要考虑它是否真的有存在价值。

## 七、怎样判断自己是否真正学会 Skill

### 7.1 最终判断标准

真正学会创建 Skill，不是能够默写 YAML，也不是完全不用 AI，而是：

> 能把一个模糊、重复的需求，定义成清楚的触发条件、输入、工作流程、资源结构、行为边界和验收标准；AI 创建以后，知道为什么这样设计，并能通过测试判断它是否合格。

### 7.2 四个学习层级

#### 第一级：会看

你能够：

- 找到 `SKILL.md`；
- 看懂 `name` 和 `description`；
- 知道 `scripts`、`references`、`templates` 大概是什么。

这是“认识零件”。

#### 第二级：会解释

你能够：

- 解释每个文件为什么存在；
- 说出删除某个文件会损失什么；
- 区分流程、知识、模板和脚本；
- 发现不必要的复杂设计。

这是“理解结构”。

#### 第三级：会设计和指挥

你能够：

- 写清五张需求卡；
- 选择单文件还是多文件结构；
- 分阶段让 AI 设计、创建和解释；
- 审查触发条件、边界和验收标准。

这是“能够负责”。

#### 第四级：会测试和迭代

你能够：

- 设计应该触发、不应触发和边界测试；
- 根据失败位置判断改哪个文件；
- 删除无用规则；
- 根据真实问题增加模板、参考资料或脚本；
- 比较有无 Skill 的实际效果。

这是“真正掌握”。

### 7.3 老板视角的验收清单

拿到 AI 创建的 Skill 后，逐项回答：

#### 目标

- 它解决的是一个真实、重复的问题吗？
- 一句话能说清它负责什么吗？
- 它有没有把多个不相关任务塞在一起？

#### 触发

- 什么情况下应该使用？
- 什么情况下不应该使用？
- `description` 是否把这两点表达清楚？

#### 流程

- 工作步骤是否符合真实做事顺序？
- 是否有不必要的步骤？
- 是否遗漏确认、验证或失败处理？

#### 资源

- 每个资源是否都有存在理由？
- `SKILL.md` 是否说明何时读取或执行？
- 是否有重复内容？
- 是否为了完整而创建空目录？

#### 风险

- 是否会覆盖文件？
- 是否会执行提交、推送、删除、发布等高影响操作？
- 哪些操作需要用户确认？
- 是否可能读取或写入敏感信息？

#### 验收

- 输出是否可检查？
- 是否定义了完成条件？
- 是否实际测试过？
- 是否在新会话中测试过？
- 是否记录了失败并修改？

如果这些问题大部分都能回答，你就不是“AI 给什么就接受什么”，而是在管理 AI 创建的能力。

### 7.4 不要求自己掌握到什么程度

作为刚开始学习 Skill 的使用者，你暂时不需要：

- 记住所有高级 frontmatter 字段；
- 独立编写复杂 Python 或 PowerShell 脚本；
- 一次设计大型自动化系统；
- 逐字符审查 AI 生成的所有代码；
- 把每个简单命令都升级成复杂 Skill。

但是，如果 Skill 涉及删除文件、推送代码、发布内容、发送消息、调用生产系统等高影响操作，就必须提高审查和测试强度。

### 7.5 最实用的自我检查

不看教程，尝试回答下面十个问题：

1. Skill 最少需要哪个文件？
2. `description` 最重要的作用是什么？
3. 工作流程应该写在哪里？
4. 长篇业务知识应该放在哪里？
5. 固定输出结构应该放在哪里？
6. 什么情况下才值得增加脚本？
7. 创建前的五张卡分别是什么？
8. 怎样防止 AI 过度设计？
9. 一个 Skill 至少要测试哪三类场景？
10. 测试失败后，怎样判断应该修改哪个文件？

如果能够用自己的话回答，并且能指挥 AI 完成一个小型 Skill，你就已经跨过了“只会看”的阶段。

## 八、一次完整的练习流程

可以按下面的顺序亲手走一遍：

### 第一步：写需求

不用 AI 创建文件，只完成 `learning-note-organizer` 的五张卡。

### 第二步：让 AI 设计

让 AI 给出最小目录和设计理由，检查是否过度设计。

### 第三步：让 AI 创建 V0.1

只创建 `SKILL.md`，不增加可选目录。

### 第四步：让 AI 逐段解释

重点理解触发、流程、边界和验收。

### 第五步：新会话测试

分别测试：

- 应该触发；
- 不应该触发；
- 边界或异常情况。

### 第六步：记录问题

不要凭感觉说“好像可以”，填写测试记录表。

### 第七步：只解决已经出现的问题

如果输出结构不稳定，增加模板；如果规则太长，增加参考资料；如果机械操作反复出错，增加并测试脚本。

### 第八步：再次测试

确认修改解决了原问题，同时没有引入新的误触发或副作用。

## 九、一页速查表

### 创建前

```text
触发卡：什么时候用？什么时候不用？
输入卡：必须提供什么？什么可以自动发现？
流程卡：按什么顺序做？
输出卡：最终交付什么？
边界与验收卡：不能做什么？怎样算完成？
```

### 资源选择

```text
执行流程               → SKILL.md
需要阅读的知识         → references/
固定输出结构           → templates/
重复、确定、易错的操作 → scripts/
最终产物需要的素材     → assets/
理想输入输出案例       → examples/
没有明确用途           → 不创建
```

### 指挥 AI

```text
第一轮：只做需求访谈
第二轮：只做结构设计
第三轮：按确认方案创建
第四轮：解释、检查和测试
```

### 测试

```text
应该触发
不应该触发
边界和异常情况
```

### 最终标准

```text
我不必亲手写完所有文件，
但我必须知道它为什么存在、什么时候使用、怎样工作、有什么风险、怎样证明合格。
```
