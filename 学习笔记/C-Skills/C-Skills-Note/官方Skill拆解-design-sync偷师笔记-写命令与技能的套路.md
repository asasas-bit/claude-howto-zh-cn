# 官方 Skill 拆解:从 design-sync 偷师写命令/技能的套路

> **学习起因**:手滑误触了系统自带的 `/design-sync`,本来想取消,结果打开一看——这是 Anthropic 官方工程师写的"重型 skill":3 份说明书 + 20 个脚本,一大堆看不懂的代码。

> 但看不懂代码不影响偷师。**这个 skill 做事的套路,和代码一点关系都没有**,而且你自己的命令里已经无意中做对了好几条。这篇笔记把它们一条条拆出来。

## 一、先认清它:这是什么、存在哪

### 1.1 它是干什么的(一句话版)

`design-sync` 的作用:**把你团队的前端组件库(按钮、输入框、卡片这些真实 React 组件)打包上传到 claude.ai/design,让那边的设计 AI 以后出设计稿时,直接用你们公司真能上线的组件来拼。**

- 没用它之前:AI 画网页用的是"通用积木",好看但和你公司实际产品不一样
- 用了它之后:AI 画出来的每张稿子都用你们的真组件,工程师能照着 1:1 写代码

所以它是给**有组件库的前端工程仓库**用的。咱们这个纯中文教程仓库没有组件,它跑不起来——但这不妨碍我们拆它的结构。

### 1.2 补齐一个知识点:skill 有三种位置

你之前学过 skill 放"项目级"和"用户级"。这次亲眼看到了第三种:

| 级别 | 在哪 | 谁放的 | 特点 |
|---|---|---|---|
| 项目级 | 项目里的 `.claude/skills/` | 你/团队 | 只这个项目用,随 git 同步,换电脑也在 |
| 用户级 | `C:\Users\你\.claude\skills\` | 你自己 | 你所有项目都能用 |
| **系统级(bundled)** | `C:\Users\你\AppData\Local\Temp\claude\bundled-skills\<版本号>\...` | **Claude Code 自带** | 官方功能,随版本升级;在临时目录里,**别手动改**(升级就被覆盖) |

`design-sync` 就是第三种:路径里的 `2.1.261` 就是 Claude Code 的版本号。它不用你安装,输入 `/design-sync` 就能调出来。

> 💡 顺带解开一个疑惑:它用 `/xxx` 的形式触发,看着像 command,**本质是 skill**。command 是单个 `.md`;它是一整个文件夹(说明书 + 脚本)。有些 skill 官方给了 `/名字` 快捷键而已。

### 1.3 它的真实结构(我实际查过)

```text
design-sync/
├── SKILL.md              ← 主说明书(调度员):判断情况、定流程、管安全
├── package-build.mjs     ← 构建脚本:把组件库转换成规定格式
├── package-validate.mjs  ← 校验脚本:产物不合格就报错
├── package-capture.mjs   ← 截图脚本:给每个组件拍预览图
├── resync.mjs            ← 增量同步:只处理有变化的部分
├── lib/                  ← 16 个共享工具脚本
├── storybook/
│   ├── SKILL.md          ← 分支 A:仓库有 Storybook 时走这里
│   └── compare.mjs 等 3 个脚本
└── non-storybook/
    └── SKILL.md          ← 分支 B:没有 Storybook 时走这里
```

合计 **3 份说明书 + 20 个脚本**。

**看不懂完全正常,而且不用焦虑**:这些脚本解决的是"几千个文件确定性转换、上传、校验"的工程问题,个人学习者一辈子不用写这种东西。值得学的是它的**做事套路**——下面 6 条,你写 command 的时候就能用。

## 二、6 条可以直接抄的套路(核心)

每条都按三部分讲:**官方怎么做 → 为什么是好套路 → 对照你自己的 [sync-upstream 命令](../../../.claude/commands/sync-upstream.md)(学习副本在 [D-command](../../D-command/sync-upstream.md))**。

### 套路 1:主文件当"调度员",不当"百科全书"

**官方怎么做**:主 `SKILL.md` 里不写所有细节。它先判断"你这个仓库有没有 Storybook",然后写一句"去读 `storybook/SKILL.md` 或 `non-storybook/SKILL.md`,按那份说明做"。主文件只管三件事:判断情况、定大流程、安全规则;具体分支的细节放在子文件里,**走到哪一步才读哪一份**。

**为什么好**:AI 干活前要把说明书读进"脑子"(上下文)。一开始只读主文件,需要哪块读哪块,脑子不被无关内容占满——省钱、少分心、不容易照着错误章节做。

> 🍳 像餐厅菜单:菜单(主文件)只列菜名和大概,具体菜谱(子文件)是厨师做到那道菜才翻的,不是进门先把整本菜谱背下来。

**对照你**:你的 sync-upstream 现在是单文件,这是**对的**——它只有四步流程,单文件最清楚。记住这个"长大的方向"就行:哪天你的命令要处理好几种不同情况(比如"有冲突时一套流程、没冲突时另一套"),就让主文件负责判断和指路,细节拆成单独文件,需要时再读。这正是[《Skill 设计、创建与验收》](Skill设计创建与验收-从会看懂到会指挥AI.md)里"先有最小 SKILL.md,确有需要时再加资源"的官方实证。

### 套路 2:要确认之前,先用"人话"解释你要批什么

**官方怎么做**:它在弹权限框**之前**,明确要求先用"没有工具术语的大白话"告诉用户你马上要批准什么。原文给的范例大意是:

> "我现在要请你批准一次:把这次跑出来的所有东西上传到新项目里,以及清理以后重建会删掉的文件。之后不会再弹框;组件验证通过一个,就在项目里出现一个。"

**为什么好**:弹窗本身只显示一串文件路径和按钮。没有这句解释,第一次用的人根本不知道自己在批什么,只能瞎点"同意"——点错了都不知道。

**对照你**:✅ **你已经在做了!** sync-upstream 在 merge 之前先展示"📋 合并预览"(上游几个新提交、合并到哪个分支),再问"确认 / 取消"。这就是同一个习惯。

**以后怎么用**:凡是要用户点"同意"的地方,前面先用一两句大白话说清:**点了会发生什么、之后还会不会再问、能不能反悔**。

### 套路 3:危险动作绝不自作主张;被拒绝就停下,不偷偷重试

**官方怎么做**(原文铁律,附翻译):

> 原文:"If the approval is denied, **stop and ask** — never continue silently, never re-prompt unasked."
> 翻译:如果批准被拒绝,**停下来问用户**——绝不默默继续,绝不没被要求就重新弹框。

建项目、上传、删除文件这类动作,全部要用户明确批准;项目创建的弹窗如果被拒绝,立刻停下问用户想怎么办,不换个法子再试。

**为什么好**:AI 最容易犯的错就是"好心办坏事"——你点拒绝,它以为你没看见,换个方式又来一遍。铁律就是堵死这个可能。

**对照你**:✅ **你也写了!** sync-upstream 里白纸黑字:"在用户明确说确认之前,不允许 merge/push""绝对不要自动 push""冲突立即停下来,不要自动解决"。你已经有这个安全基因了。

**以后怎么用**:写命令时,把"必须停下等确认"的动作显式列出来:`git push`、删除文件、发消息、上传、任何花钱的操作。别留给 Claude 自己判断"这个应该不用问吧"。

### 套路 4:干到哪记到哪,中断了能接着跑(行话叫"幂等")

**官方怎么做**,两个层面:

1. **进度落盘**:新项目一建好,立刻把项目 ID 写进 `.design-sync/config.json`。这样哪怕跑到一半整个会话挂了,重跑时它会找到**同一个**项目,不会重复建第二个。
2. **变化锚点**:每次同步完写一个 `_ds_sync.json`,记录每个组件的"内容指纹"。下次先比对指纹,没变的组件直接跳过,不用重新验证、重新上传。原文说重复上传相同文件"idempotent and cheap"(幂等且便宜)。

**为什么好**:大任务跑几小时,中途中断是常态。"记住进度"让重跑又快又安全,不会越跑越乱。

> 💾 像做表格随时 Ctrl+S,还在便签上记了"我做到第 8 步"——电脑死机了,开机接着第 8 步做,不用从头来。

**彩蛋**:它还有个 `NOTES.md`——用户中途说"这个路径不对""我们用 pnpm 不用 npm",它**立刻记下来**,下次同步不用再说第二遍。

**对照你**:✅ sync-upstream 天然满足:`git fetch` 跑多少遍都不改东西;上游没有新提交时,命令直接说"✅ 已是最新"然后结束,绝不硬 merge。你命令末尾的"注意事项"段落,扮演的就是 NOTES.md 的角色。

**以后怎么用**:写任何自动化之前问一句——"**这命令跑第二遍、第三遍,会不会出事?**"会重复发消息、重复建东西的,就让它先查状态、记住进度;踩过的坑写进注释或注意事项。

### 套路 5:开工前先设期望(要多久、花多少、能不能打断)

**官方怎么做**:第一次运行时,它先把丑话说在前面:

- 这是高保真导入,大仓库**可能要跑几个小时**
- 会用**不少 token(额度)**
- 你**随时可以打断**——中途发消息问进度、改方向,不会搞坏任何东西
- 需要你批准的事都集中在开头,之后组件会边验证边出现,你可以打开项目看着它一个个填

**为什么好**:大事先打招呼,用户有心理准备,不会以为"卡死了"而乱关;也让人敢中途插话纠偏。

**对照你**:sync-upstream 是分钟级小任务,不需要这套。但注意——**咱们现在用的 plan mode(先出方案、你批准、再动手)就是这个套路的产品化**。

**以后怎么用**:让 Claude 干"整理整个仓库""给所有笔记加目录"这种大活之前,要求它**先报计划**:大概几步、多久、要不要花很多额度。你点头再开工。

### 套路 6:验证了才算完,错误不流向下游

**官方怎么做**:每个组件的预览图都要和真实渲染截图比对、按评分标准打分,**通过了才允许上传**;还有个 `package-validate.mjs` 专门校验产物格式,不过就中止。原文的理由很直白:

> "一个组件在这里渲染错了,以后用它做的**每张设计图**都是错的。"

**为什么好**:交付前不拦住错误,后面每个使用者都替你踩坑。验证不是走流程,是防连锁反应。

**对照你**:✅ 这个仓库本身就有验证环节——改完文档跑 `uv run python scripts/validate_localization.py`;sync-upstream merge 完会显示"几个文件改动、多少增删"的统计,这是在核对结果。

**以后怎么用**:让 AI 交活时附上"怎么验证":跑哪个命令、看什么信号算成功。你自己也养成习惯——别看着像就收,拿个真实例子试一下(这正是[《老板级学习法》](老板级Skill学习法-三阶练习与外行操盘手方法论.md)说的老板第三项能力:会验收)。

## 三、4 个进阶套路(看懂就行,写复杂 skill 时回来查)

这 4 条你现在用不上,但值得"知道有这回事",以后 skill 写复杂了回来翻。

### 进阶 1:确定性的活写成脚本,判断和沟通留给 Claude

20 个 `.mjs` 脚本干的全是"机械、重复、每次都一样"的活:打包、算指纹、截图、校验格式——写成脚本一次做对、永远做对。

`SKILL.md` 干的是"需要判断"的活:这仓库是什么情况?该不该问用户?用户拒绝了怎么办?

> 你不用自己写脚本。正确姿势:流程里一旦出现"每次都一样的机械步骤",**让 Claude 把它写成脚本**放进 skill 的 `scripts/` 文件夹;你负责判断"这步该不该自动化"。

### 进阶 2:用配置覆盖默认,而不是改代码

原文的原则:"不匹配默认情况的仓库,**写配置,不要写代码**。改 `lib/*.mjs` 脚本是最后手段。"

它靠"猜"工作(猜你的构建命令、猜组件目录),猜错了不用动脚本,在 `config.json` 里写一行正确值就行。

> 启示:好工具给你留"设置项",而不是让你拆它内部。你自己设计时也一样——可能变的东西(路径、命令、名单)放在显眼的配置区,别散落在正文各处。你的 sync-upstream 里"upstream 应该指向哪个地址"就是这种配置项,还专门做了核对。

### 进阶 3:给 AI 的指令,要通过"不猜就能做"测试

官方给"写给 AI 的说明"定了条检验标准,原文:

> "每句话都要过一个测试:**AI 不用猜,就能照着做吗?**"

- ❌ 反面教材:"遵循设计系统的规范"——AI 根本不知道你的规范是什么,只能自己编
- ✅ 正面教材:"按钮用 `<Button variant="primary">`,不要自己加 class;所有页面外层包 `<ThemeProvider>`;颜色直接用 `var(--color-surface-1)` 这个 token"

> 启示:你写 command/skill 正文时,把"看着办""适当处理""按最佳实践"这种话**全部删掉**,换成具体动作:做什么、用什么名字、什么情况算完。**模糊的指令是 AI 犯错的最大来源。** 这和老板级学习法里"能清晰描述产出"是一回事,这里给了你可以逐条自检的标准。

### 进阶 4:明确写出"不要做什么"

这个 skill 里到处是 "never":绝不没被要求就重试、绝不默默继续、绝不下载大文件到本地、改脚本是最后手段……

> 启示:写给 AI 的说明书里,**"禁止事项"和"操作步骤"一样重要**。AI 不知道你的雷区,除非你写下来。你的"不要自作主张加 remote""不要自动 push"就是禁止条款——继续保持。

## 四、怎么才能写出这样的 skill

### 4.1 先打消焦虑

- 这个 skill 是官方工程师团队的产品,服务"几千个文件确定性转换上传"的工程问题,**20 个脚本你一个都不需要写**
- 你 90% 的需求,一个 command 单文件就够——你的 sync-upstream 就是证据:四步流程,真能用
- 但上面 10 条套路,**写 command 的时候就用得上**,不用等写 skill

### 4.2 skill 是"长出来的",不是"设计出来的"

对照你已经在练的[三阶练习法](老板级Skill学习法-三阶练习与外行操盘手方法论.md),你的真实进度:

| 阶段 | 内容 | 你的状态 |
|---|---|---|
| 1. 会用 command | 把重复流程写成单文件命令 | ✅ sync-upstream 真能用 |
| 2. 临摹 skill | 读现成的、照着重做 | ✅ C-Skills-Practice 里 10 个案例练过 |
| 3. 改造/原创 | 从自己的重复需求出发长出来 | 👉 下一步 |

**"长出来"的信号**:当一个 command 里出现这三样东西之一,就是它该长成 skill 的时候:

1. 反复要参考的长说明(塞正文太挤)→ 拆成 `references/`
2. 每次都一样的机械步骤 → 让 Claude 写成脚本放 `scripts/`
3. 好几种分支情况(主文件要判断"如果是 A 情况…如果是 B 情况…")→ 拆子说明

(这正是你练过的 [07-command-to-skill-migrator 案例](../C-Skills-Practice/07-command-to-skill-migrator/案例说明与创建方法.md)的思路。)

长大的方式也不是自己啃:你提需求和验收,让 Claude 拆、让 Claude 写;踩了坑记进 NOTES。**永远不要一上来就建一堆文件夹**——"先有最小 SKILL.md,需要了再加资源"。

### 4.3 运行安全六问(写进正文前,最后过一遍)

[《老板级学习法》](老板级Skill学习法-三阶练习与外行操盘手方法论.md)的 12 问管"**这个 skill 该不该做、触发得对不对**";这 6 问管"**它跑起来会不会闯祸、能不能收尾**"。两套互补,写完都过一遍:

| # | 问题 | 标准答案长什么样 |
|---|---|---|
| 1 | **流程问**:第一步做什么?最后交付什么?中间分几步? | 像 sync-upstream 那样编号写清四步 |
| 2 | **刹车问**:哪些动作必须先停下问我? | merge、push、删除、上传、发消息、花钱——逐个点名 |
| 3 | **拒绝问**:我点了"拒绝"它怎么办? | 停下、告诉我、等我指示;不偷偷重试 |
| 4 | **翻车问**:跑到一半出错/中断,烂摊子怎么收? | 冲突就停下让人解决;进度有记录,重跑不重复建设 |
| 5 | **重复问**:跑第二遍、第三遍结果会不会乱? | 不会——先查状态,没变化就说"已是最新" |
| 6 | **验证问**:做完怎么证明做对了? | 跑哪个检查命令、看什么信号算成功 |

拿 sync-upstream 当场打分:六问**全部有明确答案**(四步流程;merge/push 必停;拒绝就不动;冲突停下;fetch 幂等、无新内容即退出;merge 后报文件统计)——所以它是一个"安全的命令"。以后你写的每个命令,都争取能这样打满勾。
