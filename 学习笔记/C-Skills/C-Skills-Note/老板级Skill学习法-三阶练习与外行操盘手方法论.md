## 一、核心心态：像老板一样学 skill

真正会"当老板"的人，不用亲自写代码，但他能干**三件事**：

### 能力一：能识别"什么情况适合做 skill"

- ❌ 差的老板：看到新功能就说"帮我做一个"
- ✅ 好的老板：能判断
  - "**这个事重复出现三次以上了，值得做成 skill**"
  - "**这个事偶尔做一次，写 slash command 就够了**"

### 能力二：能清晰描述"我要什么样的产出"

- ❌ 差的老板："做一个代码审查的 skill"（AI 一脸懵，什么风格、什么范围、什么输出格式？）
- ✅ 好的老板："做一个 Python 代码审查 skill，聚焦性能和内存问题，输出按严重程度排三档，每条问题给具体行号"

### 能力三：能验收"这个 skill 是不是真的能用"

- ❌ 差的老板：AI 交上来，看着挺像那么回事，就说"好"
- ✅ 好的老板：立刻拿一个真实的坏代码去试它，看它抓不抓得住

**这三项能力，用下面的三阶练习法培养。**

## 二、三阶练习法

⚠️ **不要一上来就"让我创建一个 skill"，那太抽象了。按下面顺序来：**

---

### 🥉 第一阶段：临摹 —— 培养手感

**目标**：不是理解语法，是**看清"一个成熟 skill 长什么样"**。

**建议时长**：1-2 天。

#### 具体动作

**动作 1**：找 3 个项目里现成的 skill，**从头到尾读一遍**（不是扫，是读）。

推荐读的 skill（**从简单到复杂**，避免一上来就啃技术类）：

| Skill | 领域 | 你的看懂率 | 位置 |
|---|---|---|---|
| `blog-draft` | 写作 | 100% ✅ | `03-skills/blog-draft/SKILL.md` |
| `brand-voice` | 写作 | 100% ✅ | `03-skills/brand-voice/SKILL.md` |
| `doc-generator` | 文档 | ~80% | `03-skills/doc-generator/SKILL.md` |
| `claude-md` | 元 skill | ~80% | `03-skills/claude-md/SKILL.md` |
| `code-review-specialist` | 代码 | ~50%（技术细节难） | `03-skills/code-review-specialist/SKILL.md` |
| `refactor` | 代码 | ~50%（结构最完整） | `03-skills/refactor/SKILL.md` |

**动作 2**：读每个 skill 时，脑子里带着**这 5 个问题**：

1. 这个 skill 想解决什么**具体问题**？（用一句话说出来）
2. 它的 `description` 是怎么写的？为什么这样写能让 AI **恰好在合适的时机**触发？
3. 主文件里的 prompt 结构是"步骤指令"、"角色扮演"，还是"检查清单"？
4. 它带了 `references/` 或 `templates/` 吗？为什么带这个而不是塞进主文件？
5. 如果我要用这个 skill，我会说什么话触发它？

**动作 3**：写一份 200-500 字的短笔记，回答上面 5 个问题（3 个 skill 各写一份）。

#### 遇到技术细节看不懂怎么办？

**跳过。** 你不需要读懂所有 skill 里的技术项。你只需要：

1. **读懂结构**
2. **读懂"意图"**（这个 skill 想解决什么问题，即使你不懂技术细节）
3. **知道它存在**（以后遇到类似问题，能想起来"哦，有这么个东西"）

**你是老板。老板知道"财务部有个人专门查税"，但老板自己不需要会算税**。

**替代做法：换成你懂的领域做类比**。比如把 `code-review-specialist`（代码审查）在脑子里替换成"文章审查员"：

- description: 专业文章审查员，识别错别字、逻辑漏洞、表达不清和标点错误
- 输入：一段中文文章
- 输出：分档列出问题
- 触发：用户说"帮我看看这段文字"

**领域不同，套路一样**。

---

### 🥈 第二阶段：改造 —— 培养判断力

**目标**：不是从零创建，是**在现成的基础上改**。这个过程能让你意识到"每个部分为什么在那儿"。

**建议时长**：1 天。

⚠️ **前提**：你必须对要改造的**业务流程**有基本理解。如果是代码类 skill，最好你已经用过类似工具、或者做过一两个小项目。**否则先做第三阶段的"外行操盘手"，等有了项目经验再回来改造**。

#### 具体动作

挑一个你**已经临摹过**的 skill，让 AI 帮你改造成一个"变种"。

**例子**：把 `blog-draft` 改造成"**技术学习笔记专用起草员**"。

跟 AI 说的时候，**准确表达 4 个修改点**：

> "我要基于 `blog-draft` 做一个变种，专门针对技术学习笔记。请修改这几处：
> 1. **description**：加上"学习笔记"关键词，让它只在起草学习笔记时触发
> 2. **主文件的规则清单**：删掉博客特有的（比如引言、SEO），换成学习笔记特有的（速查表、通俗类比、常见坑）
> 3. **保留 `templates/`** —— 结构不变，但内容改成"5 段式笔记模板"
> 4. **触发例子**："帮我整理成一份关于 X 的学习笔记" 应该能触发它

**注意到没**？你已经在**当老板**了。你没有敲一行字，但你**指挥了 4 个明确的修改点**。

#### 改造完的自检问题

- 我为什么要保留 `templates/`？删了会怎样？
- 如果我不改 description，只改主文件，AI 还能正确触发这个 skill 吗？
- 这个新 skill 跟老 skill 能不能同时激活？会不会打架？

**回答这些问题的过程，就是"设计思维"在长成。**

---

### 🥇 第三阶段：原创 —— 从需求出发

**目标**：**从"我遇到了 X 问题"开始**，而不是"我想学 skill"开始。

#### 具体动作

先做一件事：**观察你自己一周内的对话历史**，找出**你重复问 AI 的东西**。

比如：

- "帮我看看这段翻译对不对" → 出现了 5 次
- "帮我总结一下今天做了啥" → 出现了 2 次
- "帮我写一份学习笔记" → 出现了 3 次

**规律**：**重复出现 3 次以上的诉求，就是 skill 的候选**。

#### 挑一个，然后写"5 行需求文档"

假设你选了 "帮我看看这段中文翻译"，别急着做 skill，先写：

```
skill 名字：translation-checker

要解决什么问题：
我经常翻译英文技术文档到中文，我想 AI 自动帮我检查翻译质量。

什么时候该自动触发：
当我贴一段中英对照文本，说"帮我看看翻译"、"这段翻译对不对"时。

我期望的输出：
- 🔴 明显错误（意思翻错）
- 🟡 表达生硬（直译痕迹重）
- 🟢 建议改进（更自然的说法）

需要用到的规则文件：
项目根的 LOCALIZATION-STYLE.md
```

**这 5 行就是你作为老板的产出**。

#### 然后交给 AI

把上面这段需求描述贴给 AI，说："**按这个需求，帮我做一个 skill**。"

AI 会给你完整的 skill 目录 + SKILL.md + references。你的工作是：

1. **验收**：立刻拿一段真实的中英对照去试，看它能不能触发、能不能抓错
2. **反馈**：如果哪里不对，具体说 "🟡 那档太少了，我想每档至少 2 条问题"、"description 应该加个 '中英对照' 关键词"
3. **迭代**：让 AI 改，再试

**这个"需求 → 生成 → 验收 → 反馈 → 迭代"的循环，就是老板的日常工作**。

## 三、老板级问答清单（12 问）

**永久收藏**。以后每次想做 skill，就按这个问一遍：

### 🎯 需求层

1. 我最近**重复做了 3 次以上**的事是什么？
2. 这件事有没有一个**清晰的"完成"标准**？
3. 我更希望它**主动触发**（skill）还是**被我叫触发**（command）？

### 📐 设计层

4. 什么样的用户输入应该触发它？给 3 个例子
5. 它需要"记住"哪些规则/模板？是塞进主文件，还是放 `references/`？
6. 输出应该长什么样？是自由文本、结构化清单、还是分档评分？

### ⚙️ 实现层（这里 AI 帮你写）

7. `allowed-tools` 需要哪些？（读文件？跑 git？调 MCP？）
8. `description` 怎么写才能既准确又不过度触发？
9. 有没有需要引用的现成文件（`@LOCALIZATION-STYLE.md`）？

### ✅ 验收层

10. 我准备了几个**测试用例**去验证它？
11. 触发关键词的**边界**在哪？（说 "看看" 触发，说 "瞄一眼" 也触发吗？）
12. 有没有可能**误触发**？比如我随口说的"翻译"就把它拉出来了

**你能回答这 12 个问题的一半，你就是合格老板**。全部能答，你就是资深产品经理级别的 skill 设计师。

## 四、外行操盘手方法论

> **场景**：不懂编程，但要用 Claude Code 做真实项目（网站、工具、AI 应用）。
>
> **前提认知**：你的场景正是 Claude Code + Skills 存在的意义 —— 让不懂技术细节的人，也能用上专家的工作流。**这不是投机取巧，是新时代的合理路径**。

### 核心思维转变

**别把"学编程"和"做项目"绑在一起。**

- **传统路径**：学编程 → 学框架 → 做项目（要 6 个月起步）
- **你的路径**：先做项目 → 边做边理解 → 缺什么补什么（做 2 周就有产出）

**AI 是你的"翻译官"**。你的工作是**问对的问题**，不是**看懂所有细节**。

### 4 个具体做法

#### 做法 1：项目拆成"业务需求"，不要拆成"技术任务"

**错误的拆法**（技术导向，你不懂）：
- 用 Next.js 搭前端
- 用 Supabase 做数据库
- 写 API endpoints
- 加 JWT 认证

**正确的拆法**（业务导向，你能想清楚）：
- 用户能注册和登录
- 用户能发一篇文章
- 用户能看到别人的文章
- 用户能点赞

**你只负责第二种拆法。第一种交给 AI**。

#### 做法 2：善用"通用 skill 库"，不要自己造轮子

你不用自己写测试的 skill、审查代码的 skill、部署的 skill。**Claude Code 内置了 10 个 bundled skills**，其中有：

- `/run` —— 帮你把代码真的跑起来
- `/verify` —— 帮你验证代码是不是真的能用
- `/security-review` —— 帮你审查代码安全
- `/code-review` —— 通用代码审查

**你的工作是"知道这些工具存在，遇到问题时能想起用它们"**。

#### 做法 3：用"外行标准工作流"做每一个功能

**5 阶段模板**：

```
【阶段 1：需求描述】（你写，200 字以内）
- 我想让用户能做什么？
- 用户看到的界面大概长什么样？（可以画歪扭的草图）
- 有没有类似的现成网站/APP 我可以指着说"就这样"？

【阶段 2：让 AI 实现】
- 把上面的需求描述贴给 Claude Code
- 让它写代码

【阶段 3：让 AI 自检】
- 让 AI 跑 /verify 或 /run，把代码真的跑一次
- 如果报错，让 AI 自己解决
- 你不用看具体报错，你只需要问"跑起来了吗？"

【阶段 4：你验收】
- 打开浏览器/APP，试一试你想要的功能
- 能用 → 下一个功能
- 不能用 → 用大白话告诉 AI 哪里不对

【阶段 5：让 AI 审查】
- 让 AI 跑 /code-review
- 如果发现严重问题，让它修
- 你不用懂严重问题是什么，你只关心"修完还能用吗"
```

**这个流程，你不需要写一行代码，但你能做出功能**。

#### 做法 4：积累"你自己的 skill 库"

做几个项目下来，你会发现你反复让 AI 做同一件事：

- 每次都让 AI **"先写代码，再跑测试"** → 做成 skill `write-and-verify`
- 每次都要 AI **"部署前先看看敏感信息有没有泄漏"** → 做成 skill `pre-deploy-check`
- 每次都让 AI **"给我总结这次改了什么"** → 做成 skill `change-summary`

**这些 skill 你完全能设计出来 —— 因为它们不是技术流程，是"你自己的工作习惯"**。

### 万能咒语：不懂技术时的三句话

**遇到看不懂代码或报错时，把这三句话当作救命稻草**：

1. **"这段代码有没有问题？"**
2. **"这个报错是什么意思？用大白话跟我说"**
3. **"这个改动会不会影响之前的功能？"**

**AI 会翻译，你负责判断"这答案对我来说是好消息还是坏消息"**。

## 五、一句话总结

### 关于 skill 学习

> **Skill 是"经验的结晶"，不是"经验的起点"。**
>
> 你不需要一上来就想"我要设计一个 xxx skill"。你只需要：
> 1. 用 AI 做项目
> 2. 记录你反复说的那些话
> 3. 等你说过 3 次同一件事，你自然想到"这可以做成 skill"
> 4. 到那时候你就知道 skill 该长什么样了
>
> **Skill 是老天赏你的礼物，不是你去山上找的宝藏**。做得多了，它自己就来。

### 关于外行做项目

> **你不是"缺少编程基础"，你是"缺少项目经验"。**
>
> 编程知识可以边做边学。但如果你不做项目，就永远没有"我遇到过这个流程"的感觉。**先动手，学习自然发生**。
